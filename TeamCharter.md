### 4.1. Політика якості та огляду коду (Lab05)

#### Стандарти кодування

Для серверної частини Rehab команда використовує **Python та FastAPI**. Основним стандартом оформлення Python-коду є **PEP 8**.

Команда дотримується таких правил:

- Назви функцій, змінних і файлів записуються у форматі `snake_case`, а назви класів — у `PascalCase`.
- Відступи в Python-коді становлять 4 пробіли.
- Функції та модулі повинні мати зрозумілі назви, які пояснюють їхнє призначення.
- Складна логіка супроводжується короткими коментарями або docstrings там, де це справді допомагає зрозуміти код.
- Не допускається зайве дублювання коду. За потреби повторювану логіку виносять в окремі функції.
- API-маршрути, моделі даних, перевірки доступу та обробка помилок розміщуються у відповідних модулях.

#### Інструменти перевірки якості

Для проєкту Rehab використовуються такі інструменти:

| Інструмент    | Призначення                                                 |
| ------------- | ----------------------------------------------------------- |
| **Black**     | Автоматичне форматування Python-коду                        |
| **Flake8**    | Перевірка стилю та типових проблем якості                   |
| **Bandit**    | Статичний аналіз Python-коду на потенційні проблеми безпеки |
| **Pytest**    | Автоматизована перевірка базової роботи API                 |
| **Gitleaks**  | Пошук випадково доданих секретів через pre-commit           |
| **pip-audit** | Перевірка Python-залежностей на відомі вразливості          |

Основні команди локальної перевірки:

```bash
python -m black --check src
python -m flake8 src
python -m bandit -r src
python -m pytest tests/test_api.py -v
```

Додаткові перевірки, налаштовані під час Lab05:

```bash
python -m pre_commit run --all-files
python -m pip_audit -r requirements.txt
```

Параметри Flake8 визначаються конфігураційним файлом `.flake8`. Для сумісності з Black використовується довжина рядка 88 символів, а правила E203, W503 та E501 вимкнено.

Під час Lab05 також підготовлено GitHub Actions workflow `code-quality.yml` та `dependency-audit.yml`. Вони призначені для перевірки якості коду та залежностей під час роботи з Pull Request і гілкою `main`. Успішність їхнього виконання на GitHub перевіряється окремо.

#### Процес Code Review

Команда використовує **GitHub Flow**: кожне окреме завдання виконується у власній гілці, після чого автор створює Pull Request до `main`.

Порядок огляду:

1. Автор перевіряє власні зміни, запускає відповідні інструменти та створює Pull Request із коротким описом зробленої роботи.
2. Інший учасник команди переглядає Pull Request. Автор не може бути єдиним рецензентом власних змін.
3. Рецензент перевіряє читабельність коду, відповідність стандартам, коректність логіки, обробку помилок, безпеку та актуальність документації.
4. Зауваження до Pull Request записуються у коментарях. Автор виправляє критичні проблеми до злиття змін.
5. Для злиття Pull Request потрібне щонайменше одне схвалення іншого учасника команди.
6. Після злиття відповідне Issue закривається, а документація оновлюється за потреби.

Особлива увага під час перевірки приділяється валідації вхідних даних, перевірці прав доступу та недопущенню потрапляння секретів у репозиторій.

#### Definition of Done — критерії завершення завдання

Для наступних змін команда встановлює такі критерії завершення завдання:

- [ ] Реалізовано заплановану функціональність або зміну.
- [ ] Код відповідає прийнятим стандартам оформлення.
- [ ] Перевірка Black проходить успішно.
- [ ] Перевірка Flake8 не містить невиправлених зауважень за активними правилами.
- [ ] Проведено перевірку Bandit; результати та виявлені ризики опрацьовано.
- [ ] Запущено відповідні автоматизовані тести; відомі помилки не залишено без пояснення.
- [ ] Не додано паролів, ключів доступу або інших секретних даних.
- [ ] Оновлено документацію, якщо зміни впливають на API, запуск або поведінку системи.
- [ ] Створено Pull Request із зрозумілим описом змін.
- [ ] Pull Request переглянутий і схвалений іншим учасником команди.
- [ ] Критичні зауваження усунуто або ризик документовано та узгоджено командою.

Для суто документаційних змін перевірки застосовуються відповідно до характеру змін: наприклад, оновлення Markdown без змін Python-коду не потребує повторного форматування Python-файлів.

#### Робота з ризиками безпеки

Результати автоматизованих перевірок не вважаються гарантією повної безпеки.

Під час Lab05 Bandit не виявив проблем за власними правилами аналізу. Водночас ручний аналіз показав ризик демонстраційної авторизації: поточні Bearer-токени не є повноцінними підписаними JWT.

Команда документує цей ризик у `docs/code-quality/static-analysis.md`. Такий механізм допустимий лише для навчального прототипу й не повинен використовуватися для реальних користувацьких даних без заміни на повноцінну авторизацію.

Під час виявлення нових проблем безпеки команда визначає рівень ризику, відповідального за виправлення та спосіб перевірки результату. Якщо ризик тимчасово приймається, причина повинна бути задокументована.

Усі учасники відповідають за якість власного коду та беруть участь у перегляді змін інших членів команди.

- Робочий процес завдань:
  1. Керівник трекера завдань створює Issue та призначає учасника, відповідального за його виконання. Кожне завдання позначається відповідним лейблом згідно з його тематикою та пріоритетом (значення лейблів наведено нижче).
  2. Кожен учасник регулярно проглядає відкриті задачі й виконує їх з урахуванням встановленого пріоритету і нагальності.
  3. Після виконання завдання учасник створює PR, у якому зазначає пов'язане Issue.
  4. Після перевірки та схвалення PR іншим учасником зміни зливаються до main, а відповідне завдання закривається.
- Лейбли:
  - high priority - найвищий пріорітет виконання;
  - medium priority - середній пріоритет виконання;
  - low priority - низький пріоритет виконання;
  - blocked - виконання завдання залежить від іншого завдання або заблоковане іншою проблемою;
  - bug - виявлена помилка або проблема в роботі системи;
  - documentation - створення чи оновлення документації;
  - duplicate - завдання дублює вже наявне Issue;
  - enhancement - новий функціонал або покращення;
  - feedback - зворотній зв'язок викладача;
  - in review - робота/код на стадії очікування/перевірки;
  - infrastructure - налаштування репозиторію та СІ;
  - invalid - неактуальне або некоректне завдання;
  - question - потребує уточнення або обговорення;
- **Практики перегляду вимог**
  - Перевірка користувацьких історій: усі користувацькі історії проходять обов'язкове рецензування Керівником якості (Марією) на відповідність критеріям INVEST та Керівником FR (Софією) перед злиттям у гілку `main`.
  - Перевірка нефункціональних вимог (NFR): перевіряються на спільній онлайн-сесії команди для підтвердження їхньої вимірюваності та коректності за стандартом ISO 25010.
