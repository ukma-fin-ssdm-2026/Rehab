# Стратегія тестування «Рехаб»

## 1. Поточний статус тестування

- Інструменти: `pytest` і `pytest-cov` (HTML-звіт), `Black` і `Flake8` у pre-commit та `bandit` (Лабораторна 5), `mutmut` для мутаційного тестування.
- Модульні тести лежать у `tests/`: `test_api.py`, `test_calendar.py`, `test_drink_summary.py`, `test_entry_details.py`, `test_goal_remaining.py`, `test_goals.py`, `test_progress.py`, `test_security.py`, `test_sobriety.py`, `test_statistics.py` (частина тестів з'явилася як результат індивідуальних TDD-вправ). Усього **ЗАПОВНИТИ N тестів** (останній прогін CI на `main`).
- Що перевіряємо: записи календаря й правило редагування, цілі та їхні граничні значення, авторизацію, підрахунок тверезих днів і статистику.
- Для налагодження використовуємо регресійні тести: помилка в `count_sober_days()` на останній день періоду зафіксована в `docs/testing/debugging-log.md`.
- TDD видно в історії комітів (теги `[RED]`, `[GREEN]`, `[REFACTOR]`).

## 2. Підсумок покриття

- Загальне покриття Backend: **ЗАПОВНИТИ %** (на початку інтеграції було 91%). Звіт: артефакт `backend-coverage-report` у CI та `htmlcov/`.
- Що лишилося непокритим: ЗАПОВНИТИ (рядки зі стовпця `Missing` у звіті CI; для кожного коротко, чому не покрито: наприклад, окремі гілки обробки помилок або службовий код).
- Високий відсоток не гарантує якості: рядок може виконатися, але нічого не перевірити. Тому ми додали мутаційне тестування, яке показує, чи тести справді ловлять зміни в коді.

## 3. Плани щодо рівнів тестування

| Рівень | Що перевіряємо | Інструмент | Коли |
|---|---|---|---|
| Інтеграційні | Endpoints календаря, цілей і статистики разом із валідацією, авторизацією та форматом помилок | `pytest` + `TestClient` | ЗАПОВНИТИ |
| Системні | Сценарій «вхід → відмітка дня → календар → ціль» на запущеному API та фронтенді | `pytest` або Postman | ЗАПОВНИТИ |
| Приймальні | Сценарії з вимог (FR) і з макета в Figma, перевірка команді та викладачу | ручна перевірка за сценаріями | ЗАПОВНИТИ |

## 4. Продуктивність, безпека, property-based

- **Продуктивність.** Ціль з NFR: p95 ≤ 500 мс при 100 користувачах. План: навантажувальний тест (`locust` або `k6`) на endpoints списку записів і статистики.
- **Безпека.** `bandit` і перевірки pre-commit (Лабораторна 5); тести на ownership (чужі записи недоступні) та ролі; перевірка загроз зі `threat-model.md` (правило 48 годин на сервері).
- **Property-based.** `Hypothesis` для підрахунку тверезих днів: кількість тверезих днів завжди між 0 і довжиною періоду, незалежно від входу. ЗАПОВНИТИ, якщо це робимо.

## 5. Інтеграція в CI/CD

- Workflow `.github/workflows/ci.yml` запускається на кожен push і Pull Request у `main`.
- Job `backend-tests` виконується на self-hosted Linux runner: Python 3.12, встановлення залежностей з `requirements.txt`, потім `python -m pytest -q --cov=backend.app --cov-report=term-missing --cov-report=html:htmlcov`.
- HTML-звіт покриття зберігається як артефакт збірки `backend-coverage-report`.
- У репозиторії також працюють окремі перевірки `Code Quality` і `Dependency Audit`.
- Наступні кроки: додати поріг покриття (`--cov-fail-under`) та облік гілок (`--cov-branch`); не зливати Pull Request без зеленого прогону й approve колеги (політика з `TeamCharter.md`); мутаційне тестування запускати періодично, а не на кожен PR, бо воно повільне.
