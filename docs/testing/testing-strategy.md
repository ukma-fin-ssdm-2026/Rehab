# Стратегія тестування «Рехаб»


## 1. Поточний статус тестування


- Інструменти: `pytest` і `pytest-cov` (HTML-звіт), `Black` і `Flake8` у pre-commit та `bandit` (Лабораторна 5), `mutmut` для мутаційного тестування.
- Модульні тести лежать у `tests/`: `test_api.py`, `test_calendar.py`, `test_drink_summary.py`, `test_entry_details.py`, `test_formatting.py`, `test_goal_remaining.py`, `test_goals.py`, `test_progress.py`, `test_security.py`, `test_sobriety.py`, `test_statistics.py` (частина тестів з'явилася як результат індивідуальних TDD-вправ). Усього **114 тестів**, усі успішні (останній прогін CI; цифри враховують гілку `tdd/format-days`, після її злиття в `main` вони перевіряються повторно).
- Що перевіряємо: записи календаря й правило редагування, цілі та їхні граничні значення, авторизацію, підрахунок тверезих днів, форматування й статистику.
- Для налагодження використовуємо регресійні тести: помилка в `count_sober_days()` на останній день періоду зафіксована в `docs/testing/debugging-log.md`.
- TDD видно в історії комітів (теги `[RED]`, `[GREEN]`, `[REFACTOR]`).


## 2. Підсумок покриття


- Загальне покриття Backend: **99%** (354 із 357 операторів; на початку інтеграції було 91%). Звіт: артефакт `backend-coverage-report` у CI та `htmlcov/`.
- Що лишилося непокритим (3 рядки, усі в гілках обробки помилок, які ще не викликані тестами):
  - `main.py:86`: обробка `HTTPException` без структурованого `detail` (наприклад, неіснуючий маршрут);
  - `models.py:86`: `ValueError` у валідаторі, що забороняє тригер для тверезого дня;
  - `routers/calendar.py:108`: помилка `INVALID_DATE_RANGE`, коли `from` пізніше за `to`.


  Кожен із цих рядків можна закрити окремим негативним тестом.
- Високий відсоток не гарантує якості: рядок може виконатися, але нічого не перевірити. Тому ми додали мутаційне тестування, яке показує, чи тести справді ловлять зміни в коді.


## 3. Підхід до рівнів тестування


- **Модульні** тести покривають основну частину логіки (сервіси, моделі, безпека).
- **Інтеграційні** тести перевіряють endpoints календаря, цілей і статистики разом із валідацією, авторизацією та форматом помилок через `pytest` + `TestClient`; частину таких перевірок уже містить `test_api.py`.
- **Системні та приймальні** перевірки будуються на сценаріях з вимог (FR) і макета в Figma («вхід → відмітка дня → календар → ціль»). Їх розширюватимемо в міру росту проєкту.


## 4. Продуктивність, безпека, property-based


- **Продуктивність.** Ціль з NFR: p95 ≤ 500 мс при 100 користувачах. Навантажувальні тести (`locust` або `k6`) на endpoints списку записів і статистики ще не виконані.
- **Безпека.** `bandit` і перевірки pre-commit (Лабораторна 5); тести на ownership та ролі; перевірка загроз зі `threat-model.md`.
- **Property-based.** Планується `Hypothesis` для підрахунку тверезих днів: кількість тверезих днів завжди між 0 і довжиною періоду.


## 5. Інтеграція в CI/CD


- Workflow `.github/workflows/ci.yml` запускається на кожен push і Pull Request у `main`.
- Job `backend-tests` виконується на self-hosted Linux runner: Python 3.12, встановлення залежностей з `requirements.txt`, потім `python -m pytest -q --cov=backend.app --cov-report=term-missing --cov-report=html:htmlcov`.
- HTML-звіт покриття зберігається як артефакт збірки `backend-coverage-report`.
- У репозиторії також працюють окремі перевірки `Code Quality` і `Dependency Audit`.
- Наступні кроки: додати поріг покриття (`--cov-fail-under`) та облік гілок (`--cov-branch`); не зливати Pull Request без зеленого прогону й approve колеги (політика з `TeamCharter.md`); мутаційне тестування запускати періодично, а не на кожен PR, бо воно повільне.
