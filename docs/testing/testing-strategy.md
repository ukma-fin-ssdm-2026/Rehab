# Стратегія тестування Rehab

## Рівні перевірок

- Модульні: розрахунок серій/періодів/цілей, Pydantic-схеми, стилі, нагадування, фото й безпека.
- Інтеграційні: TestClient + справжні JWT та PostgreSQL; API авторизації, календаря, профілю, менторства, повідомлень, підтримки, скарг, admin і job.
- Конкурентні: повторні приєднання, коментарі й події, взаємні скарги, нагадування та порядок блокувань. Важлива перевірка відсутності дублів і відкату всієї операції.
- Frontend Node tests: API-клієнт, сесії й запізнілі відповіді, навігація, календар, прогрес, inbox, менторство, стилі та фото. TypeScript, Expo lint і web export перевіряють сумісність та збірку.
- Ручне приймання: пов’язані екрани й публічний deployment; мобільний браузер — тільки iPhone/Safari.

## Середовище й запуск

Тільки окрема тестова PostgreSQL із захищеним TEST_DATABASE_URL; pytest очищає її дані. Онлайн-БД не використовується. Прогони зі спільною тестовою БД виконуються послідовно. Листи в тестах не відправляються в мережу; реальний Gmail перевіряється окремо після OAuth.

Команди та залежності: [setup_and_run.md](../../setup_and_run.md). CI: [.github/workflows/ci.yml](../../.github/workflows/ci.yml), якість і залежності перевіряють окремі workflows. Звіти coverage прив’язані до SHA, а не до постійного числа в документації. Охоплення рядків не замінює перевірку поведінки; мутаційні лабораторні результати наведено окремо в [mutation-testing.md](mutation-testing.md).

## Критерії та докази

[Тест-план](../validation/test-plan.md) зберігає критерії, номери кейсів і межі ручного приймання. [RTM](../requirements/rtm.md) пов’язує їх з вимогами; scripts/check_traceability.py перевіряє узгодженість, а не факт виконання.

Для релізного SHA потрібні успішні актуальні CI/якість, відсутність критичних дефектів та спільне онлайн-приймання. Історичні лабораторні 99% coverage і вимірювання прототипу не є метриками поточної реалізації. PERF-001 перевіряється окремим навантаженням, REL-001 — тривалим моніторингом; доступність Free-хостингу не вважається гарантованою.

## Системний і приймальний рівні: інструменти та сценарії

| Сценарій | Інструмент | Очікування |
|---|---|---|
| Auth → calendar → progress → inbox → support | pytest/TestClient + PostgreSQL, test_calendar_message_flow.py | Реальні JWT, атомарність, оновлені серії й одна подія |
| Code → relapse → support → complaint → admin decision | pytest/TestClient + PostgreSQL, test_system_integration.py | Доступ відкритий лише активній парі й закритий після рішення |
| Публічні форми/навігація/reload/фото/стилі | Справжній iPhone, Safari; модель/iOS/SHA в протоколі | Збереження стану, коректні прямі URL, приватність між акаунтами |
| Справжній email | Gmail OAuth + контрольний job, перевірка скриньки власницею | Opt-in лист реально отриманий один раз; тестовий sender цього не доводить |
| Перезапуск і deployment | Render dashboard + /health /ready + повторний вхід | Дані збережені, API і frontend відповідають перевіреним SHA |

Команда фіксує дату, середовище, SHA та фактичний результат у тест-плані/інструкції розгортання. Невиконаний сценарій позначається запланованим. Поточний Locust з demo-токеном є історичним артефактом і не використовується для заяв про продуктивність нового JWT API.
