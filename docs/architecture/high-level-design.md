# Високорівнева архітектура Rehab

Стан інтегрованого релізу перед КТ3, 30.10.2026. Онлайн-приймання КТ2
підтверджено Поліною; [результати](../validation/calendar-kt2.md).

## 1. Архітектурний стиль

Клієнт-серверний застосунок: Expo Web і FastAPI із багатошаровою монолітною
серверною частиною. Маршрути перевіряють HTTP-контракт і права, сервіси
обчислюють прогрес, репозиторії працюють із PostgreSQL через SQLAlchemy/psycopg.
Окремі мікросервіси не потрібні для погодженого обсягу.

## 2. Реалізовані компоненти

- **Expo Web:** реєстрація/вхід, onboarding, профіль, календар, деталі та форми,
  головна, статистика, фіксовані етапи 7/30, адміністрування й діаграма тригерів.
- **Спільний apiRequest:** JSON через HTTPS, JWT поточної сесії, завершення
  недійсної сесії без скидання новішого входу через запізнілу відповідь.
- **FastAPI:** auth, calendar_postgres, goals/statistics, admin, health/readiness.
  Захищені операції використовують поточного користувача й перевірку блокування.
- **PostgreSQL:** користувачі та календарні записи; goals залишена як legacy-таблиця
  початкової міграції й не використовується застосунком для етапів.
- **Розрахунки:** прогрес та етапи походять із календаря; найдовша серія визначає
  досягнення 7/30, поточна — прогрес невиконаного етапу. Особистих CRUD-цілей немає.

Менторство, чати, сповіщення та скарги не реалізовані в цьому релізі.
Сторінка підтримки пояснює цей стан. Майбутні сутності з початкових матеріалів
Лаб 3 не слід вважати наявними таблицями або API.

## 3. Середовища та межі

Браузер отримує статичний frontend із Render і напряму викликає API Render
через HTTPS/JSON. API звертається до Neon через PostgreSQL із TLS та пулом
з'єднань. CORS дозволяє погоджений origin клієнта. Локально Compose запускає
окремі PostgreSQL 16 dev/test; онлайн — Neon PostgreSQL 18.

JWT зберігається в sessionStorage вкладки; пароль хешується Argon2.
Права й власність перевіряє сервер, а не стан інтерфейсу. Seed запускається
явно; старт API не скидає БД. [Розгортання](../deployment/render-neon.md).

## 5. Календар і цілісність даних

`/api/v1/auth/me` повертає current_date (Europe/Kyiv) та tracking_start_date.
Запис дозволений у цьому включному діапазоні. Пропущений день у діапазоні
рахується тверезим, але UI пояснює відсутність окремого збереженого запису.

POST/PATCH календаря блокують рядок користувача, змінюють запис,
викликають recompute_progress та виконують один commit. Помилка перерахунку
відкочує транзакцію. UNIQUE(user_id,date) захищає від дублікатів.

PATCH змінює лише status/trigger_category протягом 48 годин включно від
created_at (UTC). Sober очищує напої й тригер, зберігаючи коментар.
Дату, власника й час створення змінювати не можна.

Клієнт оновлює календар при фокусі й сповіщає екрани прогресу після мутацій.
Деталі `/entry/{record_id}` підтримують reload; безпечне посилання відновлюється
після входу, а сервер повторно перевіряє власника.

Pydantic EntryCreate/EntryUpdate/EntryOut задають HTTP-контракт;
SQLAlchemy DayRecord задає таблицю day_records. Це різні рівні моделювання.
[Модель даних](data-model.md), [контракт БД](../development/database-handoff.md).
