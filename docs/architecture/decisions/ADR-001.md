# ADR-001: Вибір архітектурного стилю системи

**Статус:** Прийнято  
**Дата:** 2026-09-30  

## Контекст
Згідно з функціональними вимогами (FR) з Лабораторної 2, система "Рехаб" повинна забезпечувати роботу з профілями користувачів, ведення календаря відміток, підрахунок серій (streaks) та зв'язок "ментор-підопічний". Нефункціональні вимоги (NFR) диктують жорсткі терміни розробки MVP силами команди з 4 студентів. Нам потрібна архітектура, яка мінімізує накладні витрати на інфраструктуру, але забезпечує чіткий логічний поділ коду.

## Рішення
Використовувати клієнт-серверну архітектуру із серверною частиною у вигляді Багатошарового моноліту (Layered Monolith).

## Наслідки
* **Позитивні:** Забезпечує найшвидший час виходу на ринок (Time-to-market). Вся бізнес-логіка знаходиться в єдиній кодовій базі, що робить локальне тестування та розгортання максимально простими. Відсутня потреба у налаштуванні складних мережевих викликів між сервісами.
* **Застереження:** Вимагає суворої дисципліни від команди щодо дотримання меж шарів (контролери не повинні ходити напряму в базу даних), інакше моноліт швидко перетвориться на непідтримуваний "спагетті-код".
* **Негативні:** Система масштабується лише цілком. Якщо навантаження зросте виключно на модуль розрахунку статистики, доведеться розгортати додаткові копії всього моноліту. Також це ускладнює впровадження нових технологічних стеків у майбутньому.

## Розглянуті альтернативи
1. **Мікросервісна архітектура (Microservices):** Відхилено через надмірну складність (overengineering). Налаштування міжсервісної комунікації, API-шлюзів та розподілених транзакцій забере весь час, відведений на розробку MVP.
2. **Serverless (Функції як сервіс - AWS Lambda):** Відхилено через ризик "vendor lock-in" (прив'язки до конкретного хмарного провайдера) та ускладнене локальне налагодження (debugging), що критично для навчального процесу.
