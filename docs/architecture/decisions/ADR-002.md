# ADR-002: Вибір системи управління базами даних (СУБД)

**Статус:** Прийнято  
**Дата:** 2026-09-30  

## Реалізація рішення

Для локальної розробки й інтеграційних тестів використовуються окремі PostgreSQL 16
у Compose, SQLAlchemy 2.x, psycopg 3 та Alembic. Міграція `0001_initial` задає
таблиці users/day_records/goals; автоматичного скидання при запуску API немає.
Напої — JSONB-масив одного day_records, оскільки окремий керований довідник
напоїв не входить у поточну реалізацію. Додавання такого довідника потребуватиме
наступної міграції, а не редагування вже застосованої початкової.

Назви dev- і test-баз повинні різнитися; додаткові параметри URL не можуть
перевизначати адресу або ім’я перевіреного підключення. Обидва середовища
перевіряються на PostgreSQL, не на SQLite. HTTP-маршрути вже переведені на БД після інтеграції авторизації та статистики.
Онлайн використовується Neon PostgreSQL 18, локально — PostgreSQL 16.
Міграція 0002_team_foundation додає профіль, фото, менторство, повідомлення, скарги й поштову чергу; чинні етапи 7/30/90/180/365 обчислюються без CRUD goals.
Перезапуск API не змінює таблиці; збереження даних після нього підтверджено
ручним онлайн-тестом Поліни 2026-10-29.

## Контекст
Система "Рехаб" (згідно з FR) фіксує щоденні відмітки користувачів та розраховує прогрес цілей. Дані мають жорстку реляційну структуру: відмітка не може існувати без користувача, а ментор може переглядати лише прив'язаних до нього підопічних. Відповідно до NFR щодо надійності, система не може допускати втрати даних про прогрес або їх неузгодженості у випадку системного збою.

## Рішення
Використовувати реляційну систему управління базами даних PostgreSQL.

## Наслідки
* **Позитивні:** Гарантує транзакційну цілісність даних (повна відповідність вимогам ACID). Вбудовані механізми зовнішніх ключів (Foreign Keys) надійно захищають структуру зв'язків між сутностями. 
* **Застереження:** Зміни в моделі даних вимагатимуть обов'язкового створення міграцій (зміна схем таблиць), що уповільнює внесення змін на пізніх етапах розробки.
* **Негативні:** Горизонтальне масштабування (додавання нових серверів для запису даних) реалізується значно складніше порівняно з NoSQL рішеннями.

## Розглянуті альтернативи
1. **MongoDB (NoSQL документо-орієнтована БД):** Відхилено, оскільки наші дані є сильно пов'язаними (реляційними). Використання NoSQL змусило б реалізовувати перевірку цілісності зв'язків на рівні коду застосунку, що підвищує ризик помилок.
2. **SQLite:** Відхилено через обмеження паралельного запису. SQLite добре підходить для локального тестування, але не витримає одночасних запитів від багатьох клієнтів у виробничому середовищі (Production).
