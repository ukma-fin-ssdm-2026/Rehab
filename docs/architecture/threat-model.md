# Модель загроз (Threat Model - STRIDE)

Цей документ містить результати формалізованого моделювання загроз за методом **STRIDE** для вебзастосунку «Рехаб».

## 1. Архітектурні межі довіри (Trust Boundaries)
1. **TB-1 (Клієнтська зона):** Браузер користувача / Frontend, недовірена зона під контролем користувача.
2. **TB-2 (Серверна зона):** Backend API / бізнес-логіка, захищена довірена зона.
3. **TB-3 (Зона зберігання даних):** База даних PostgreSQL, ізольоване внутрішнє сховище чутливих даних.

---

## 2. Таблиця загроз за методом STRIDE

| Компонент / Межа | Категорія STRIDE | Опис детального сценарію загрози | Оцінка ризику | Планований контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **TB-1 ➔ TB-2**<br>(Браузер ↔ Backend API) | **Spoofing**<br>(Підробка особи) | Зловмисник намагається перехопити токен або згенерувати фальшивий JWT-токен із підробленим ідентифікатором, щоб видати себе за адміністратора чи ментора та отримати доступ до панелі модерації. | Висока | Використання криптографічно стійких підписів токенів, короткий час життя сесії (Access Token), зберігання JWT у sessionStorage (ризик XSS лишається; HttpOnly cookies не реалізовані) та серверна перевірка ролей (`user`, `mentor`, `admin`). |
| **TB-1 ➔ TB-2**<br>(Клієнт ↔ Серверні ендпоінти) | **Tampering**<br>(Модифікація даних) | Користувач перехоплює HTTP-запит на оновлення щоденного запису (`DayRecord`) і намагається штучно змінити дату, статус чи обійти бізнес-обмеження (наприклад, змінити історію тверезості заднім числом). | Середня | Повна заборона довіри до клієнтської логіки. Перенесення всіх валідацій (зокрема перевірки часового інтервалу 48 годин на основі серверного поля `created_at`) виключно на бекенд. |
| **TB-2 ➔ TB-3**<br>(Бекенд API ↔ База даних) | **Repudiation**<br>(Невідмовність) | Адміністратор системи виконує деструктивну дію (наприклад, приймає рішення щодо скарги), а потім заперечує це. Через відсутність системного аудиту довести відповідальність неможливо. | Низька | Впровадження захищеного журналу аудиту (Audit Trail). Логування всіх критичних адміністративних операцій в окрему таблицю з міткою часу та ID адміністратора. |
| **TB-2 ➔ TB-3**<br>(Модуль аналітики ➔ БД) | **Information Disclosure**<br>(Витік інформації) | Неавторизований користувач звертається до відкритих статистичних ендпоінтів та отримує доступ до чутливих психологічних даних (детальні причини зривів, категорії тригерів, email). | Висока | Застосування суворої анонімізації та агрегації даних для глобальних звітів (US-006). Шифрування каналів зв'язку (SSL/TLS) та обмеження доступу до персональних полів на рівні SQL-запитів. |
| **TB-1 ➔ TB-2**<br>(Зовнішній клієнт ➔ API) | **Denial of Service**<br>(Відмова в обслуговуванні) | Зловмисник запускає скрипт масового надсилання запитів (Flood / Brute-force) на створення щоденних звітів або авторизацію, перевантажуючи сервер та позбавляючи користувачів доступу. | Середня | Налаштування обмеження кількості запитів (Rate Limiting) за IP та токеном на рівні API-шлюзу, оптимізація індексів бази даних. |
| **TB-1 ➔ TB-2**<br>(Сесія користувача ➔ API адміна) | **Elevation of Privilege**<br>(Підвищення привілеїв) | Звичайний користувач із роллю `user` намагається напряму надіслати API-запити, призначені виключно для адміністраторів (наприклад, ендпоінти перегляду скарг). | Висока | Проєктування багаторівневої системи контролю доступу (RBAC). Реалізація серверних перевірок прав (Authorization Middleware) для кожного адміністративного маршруту. |

## Статус контрзаходів

JWT/Argon2, перевірки ролі, власника й активного зв’язку, Pydantic-валідація та обмеження БД реалізовані. Поля рішення скарги фіксують адміністратора й час, але це не окремий незмінний audit trail. Rate limiting та HttpOnly cookies залишаються можливими посиленнями, а не реалізованими гарантіями. Gmail OAuth і X-Job-Token є окремими секретами; персональні повідомлення й фото не повинні потрапляти в журнали. Схвалення скарги закриває пару, а не акаунт.

## Зв’язок із діаграмами

| STRIDE | Компоненти / межа | Контроль у реалізації або залишковий ризик |
|---|---|---|
| Spoofing | Browser/Web → Routes/Security, TB-1→TB-2 | JWT підпис/строк/token_version, Argon2; sessionStorage не захищає від XSS |
| Tampering | Calendar Routes → Services → DB, TB-2→TB-3 | Власник, Pydantic, 48 годин для PATCH, унікальність дати, транзакція |
| Repudiation | Admin Routes → Complaints → DB | Зберігаються автор рішення й час; окремого незмінного audit trail немає |
| Information Disclosure | Web → Mentorship/Notifications/Admin Routes → DB | Активний зв’язок, приватний inbox і фото, адміну лише доказ та агрегати |
| Denial of Service | Browser/Actions → API/Job | Розміри фото, межі сторінок, advisory lock; gateway/rate limiter не реалізовані |
| Elevation of Privilege | Browser → Admin Routes / Services | require_role(admin), захист role injection; код ментора не відкриває довільний чужий ресурс |

Назви відповідають [компонентам](uml/component-diagram.puml) і [розгортанню](uml/deployment-diagram.puml). Gmail отримує лише opt-in нагадування, а не календар чи коментарі; секрети OAuth і job не передаються Web.
