# Lab 10 — звірка DORA між CI Pipeline і Code Quality

**Роль:** аналітик DORA (учасник №2).  
**Репозиторій:** [Rehab](https://github.com/ukma-fin-ssdm-2026/Rehab).  
**Період:** 27.10–16.11.2026 включно (21 доба, UTC).  
**Джерела:** GitHub Actions REST API; 54 merge-коміти, зіставлені за повним SHA.

## Межі порівняння

Вихідний [розрахунок DORA](./dora-metrics.md) враховував лише `CI Pipeline` для `push` у `main`. Це коректна, але вузька вибірка: вона не перевіряє, чи проходив цей самий коміт також `Code Quality`. Для розширеного варіанта кожному із 54 комітів зіставлено один `CI Pipeline` та один `Code Quality` на тому самому SHA. **Коміт вважається успішним, тільки якщо обидва workflow завершені зі статусом `success`**; якщо хоча б один завершено з `failure`, коміт невдалий. `Queued` без завершеного результату не вважається ні успіхом, ні збоєм.

Усього **54 коміти**: **51 успішний**, **2 невдалі**, **1 незавершений**. Усі 54 відповідності з двома посиланнями на запуски наведено в [таблиці за комітами](./dora-cross-workflow-commits.csv).

## Чотири метрики: базова й розширена вибірка

| Метрика | Лише CI Pipeline | CI Pipeline + Code Quality |
| --- | ---: | ---: |
| Deployment Frequency (CI-проксі) | **2,52** успішних CI/день (53 / 21) | **2,43** повністю зелених коміти/день (51 / 21) |
| Lead Time for Changes (CI-проксі), медіана | **1,44 год** (53 PR) | **1,33 год** (51 PR) |
| Lead Time for Changes, середнє | **15,91 год** | **14,03 год** |
| Change Failure Rate (CI-проксі) | **0,00%** (0 / 53) | **3,77%** (2 / 53) |
| Time to Restore Service (CI-проксі) | **Не визначається** | **20,48 год**, один епізод відновлення |

**Частота за тижнями в розширеній вибірці:** 25 успішних комітів за 27.10–02.11; 20 за 03.11–09.11; 6 за 10.11–16.11. Разом 51. Базова вибірка дає 27 / 20 / 6.

### Формули й правило кінцевої дати

- **Частота:** кількість комітів, для яких успішно завершилися обидва workflow, поділена на 21 день. Один SHA рахується один раз, а не двічі за кількістю workflow.
- **Lead Time:** для кожного повністю зеленого PR — від `author.date` найранішого коміту PR до **найпізнішого `jobs.completed_at` серед двох workflow** відповідного merge SHA. Усі 51 значення обчислено за часовими позначками без попереднього округлення. Медіана 1,3311 год; середнє 14,0306 год.
- **Частка збоїв:** 2 невдалі коміти / (51 успішний + 2 невдалі завершені коміти) × 100% = **3,7736%**. Один незавершений коміт виключено зі знаменника. Не можна рахувати два workflow одного коміту як дві поставки.
- **Відновлення:** від завершення першого невдалого `Code Quality` до моменту, коли наступний коміт має обидва зелені workflow. Для єдиного інциденту цей інтервал дорівнює **20 год 28 хв 42 с = 20,4783 год**. Це **одне спостереження**, а не середнє за кількома інцидентами.

Значення **≈20,47 год** відповідає моменту зеленого `Code Quality` окремо; **≈20,48 год** — підтвердженню обома workflow, яке обране для розширеної методики.

## Як інтерпретувати відмінності

Базові показники лишаються правильними **для явно обмеженого `CI Pipeline`**. Розширений варіант описує стан коміту точніше: один зелений workflow не приховує іншого червоного. Медіана Lead Time стала меншою, тому що два PR з невдалим `Code Quality` не входять до вибірки повністю зелених комітів, а не тому, що CI раптом пришвидшився.

Додатково для тих самих SHA перевірено `Dependency Audit` (53 `success`, 1 `queued`) і `Lab07 Traceability` (45 `success`, 1 `queued`, workflow наявний для 46 SHA). Додаткових завершених збоїв у них не знайдено. `Publish API docs` не включено до критерію успішної доставки: у ньому є скасовані запуски, які не можна автоматично прирівнювати до невдалих перевірок коду.

Зміни для бонусу №2, злиті 18.11.2026 у [PR #272](https://github.com/ukma-fin-ssdm-2026/Rehab/pull/272), **не змінюють заднім числом** дані за 27.10–16.11.2026. Водночас `paths-ignore` впливатиме на подальше зіставлення частоти CI та числа злиттів документації.
