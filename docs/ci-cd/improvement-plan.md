## 2. Першопричини

### Технічні

1. **Пікова черга на спільних раннерах перед дедлайном.** 01.11 увечері (дедлайн курсу) запуск PR #233 чекав раннер 64,8 хв, PR #228 — 15,9 хв. Раннери спільні для всіх команд, тож частину черги ми не контролюємо, але власні зайві запуски її збільшують.
2. **Зайві запуски.** Більше половини злиттів у `main` змінювали лише документацію, але запускали всі чотири workflow. Застарілі запуски PR після нового push не скасовувалися.
3. **Повільніший CI після додавання інтеграційних тестів.** З 01.11 backend-тести з PostgreSQL збільшили виконання з ~0,5 до ~2 хв (медіана), з піками до 8,6 хв. Ці тести запускалися на кожен PR.
4. **Перевірка форматування лише в CI.** Black запускається тільки в Code Quality, локально перед push — ні. Невідформатований файл виявляється вже після push.
5. **Завислий запуск без обмеження.** Запуски для злиття PR #261 стоять у черзі 7 днів; ніхто їх не скасував і не перезапустив, тож коміт залишився без підтвердженого зеленого стану.

### Організаційні та культурні

1. **PR довго чекають злиття.** PR #242 — 129,5 год, #153 — 104,8 год, #206 — 98,3 год від першого коміту. Немає домовленості, за скільки часу PR має отримати рецензію.
2. **Злиття пачками перед дедлайнами.** Роботу зливають за день-два до здачі, а не впродовж тижня. Через це пікові черги збігаються з дедлайнами й спільним навантаженням інших команд.
3. **Червону перевірку ігнорують, якщо вона «не наша».** PR #153 і #156 злиті при червоному quality-check у PR. Ніхто не відповідав за стан `main`, тож червоний Code Quality не полагодили одразу.
4. **Метрика «бачить» лише CI Pipeline.** У вибірку DORA увійшов лише CI Pipeline, тому частота збоїв змін 0%, хоча `main` двічі був червоним за Code Quality.

## 5. Читання парами

- **Швидкість + стабільність.** Частота розгортань висока (17,7 зелених запусків на тиждень), а частота збоїв змін 0% для CI Pipeline. Це не означає, що команда жертвує стабільністю заради швидкості, але й 0% неповне: Code Quality показує реальний збій, який метрика не врахувала.
- **Час виконання змін + час відновлення.** Конвеєр швидкий (виконання ~2 хв), але і зміни, і відновлення гальмують люди: PR чекають рецензії днями, а червоний `main` чекав виправлення ~20 год. Обидві метрики покращуються однаковими організаційними діями — швидшою рецензією і відповідальністю за стан `main`.
- **Ціна бонусів 2 і 3.** Пропуск документаційних злиттів знижує формальну частоту розгортань; повільний набір тестів лише після злиття може дати червоний `main`, якого раніше не було (дефект ловиться пізніше), тобто підвищити частоту збоїв змін.
