## 2. Першопричини

### Технічні

1. **Пікова черга на спільних раннерах перед дедлайном.** 01.11 увечері (дедлайн курсу) запуск PR #233 чекав раннер 64,8 хв, PR #228 — 15,9 хв. Раннери спільні для всіх команд, тож частину черги ми не контролюємо, але власні зайві запуски її збільшують.
2. **Зайві запуски.** Більше половини злиттів у `main` змінювали лише документацію, але запускали всі чотири workflow. Застарілі запуски PR після нового push не скасовувалися.
3. **Повільніший CI після додавання інтеграційних тестів.** З 01.11 backend-тести з PostgreSQL збільшили виконання з ~0,5 до ~2 хв (медіана), з піками до 8,6 хв. Ці тести запускалися на кожен PR.
4. **Локальна перевірка форматування не гарантована.** У репозиторії є [`.pre-commit-config.yaml`](../../.pre-commit-config.yaml) з Black, але хук треба встановити кожній учасниці (`pre-commit install`), і з логів CI не видно, чи запускали його локально. Невідформатований файл дійшов до `main`, тобто принаймні в цьому випадку локальна перевірка не спрацювала.
5. **Завислий запуск без обмеження.** Запуски для злиття PR #261 стоять у черзі 7 днів; ніхто їх не скасував і не перезапустив, тож коміт залишився без підтвердженого зеленого стану.

### Організаційні та культурні

1. **Окремі PR довго чекають злиття.** Більшість PR рецензують за менше ніж годину, але 8 із 53 чекали злиття понад добу: #153 — 102,1 год до першої рецензії, #257 — 72,5 год, #260 — 53,5 год, #206 — 50,4 год. Домовленості, за скільки часу PR має отримати рецензію, немає. Чому саме ці PR чекали (вихідні, дедлайни інших курсів, залежність від інших PR), з даних GitHub не видно — це гіпотеза для обговорення в команді. Найдовша зміна, #242 (129,5 год), чекала не рецензії, а довго розроблялася до відкриття PR (129,1 год).
2. **Злиття пачками перед дедлайнами.** Роботу зливають за день-два до здачі, а не впродовж тижня. Через це пікові черги збігаються з дедлайнами й спільним навантаженням інших команд.
3. **Червона перевірка не зупинила злиття.** PR #153 і #156 злиті при червоному quality-check у PR. Відповідальної за стан `main` не було призначено, і червоний Code Quality полагодили лише наступного дня. Чому PR злили попри червону перевірку, з даних не видно; ймовірно, її сприйняли як не пов'язану зі змінами PR.
4. **Вибірка DORA охоплює лише CI Pipeline.** Для цієї вибірки частота збоїв змін 0% — коректний результат із зазначеним обмеженням. Але Code Quality за той самий період двічі був червоним на `main`. Якщо врахувати і його, метрики треба перерахувати за комітами: один SHA — один запис, червоний, якщо червоний хоч один врахований workflow, без подвійного рахування.

## 5. Читання парами

- **Швидкість + стабільність.** Частота розгортань висока (17,7 зелених запусків на тиждень), а частота збоїв змін 0% для вибірки CI Pipeline. Ознак того, що швидкість досягається коштом стабільності, у цій вибірці немає. Водночас Code Quality показує збій, який вибірка не охоплює, тому 0% треба читати разом із цим обмеженням.
- **Час виконання змін + час відновлення.** Конвеєр швидкий (виконання ~2 хв), але і зміни, і відновлення гальмують люди: PR чекають рецензії днями, а червоний `main` чекав виправлення ~20 год. Обидві метрики, ймовірно, покращаться від однакових організаційних дій — домовленості про строк рецензії і відповідальності за стан `main`. Це гіпотеза, яку варто перевірити на наступному періоді.
- **Ціна бонусів 2 і 3.** Пропуск документаційних злиттів знижує формальну частоту розгортань; повільний набір тестів лише після злиття може дати червоний `main`, якого раніше не було (дефект ловиться пізніше), тобто підвищити частоту збоїв змін.
