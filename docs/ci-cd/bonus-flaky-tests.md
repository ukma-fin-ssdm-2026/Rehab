# Lab10 — бонус №4: пошук нестабільних тестів

## Реалізація

- Workflow: [.github/workflows/flaky-tests.yml](../../.github/workflows/flaky-tests.yml).
- Аналізатор і послідовний запуск: [scripts/check_flaky_tests.py](../../scripts/check_flaky_tests.py).
- Контрактні перевірки: [scripts/test_check_flaky_tests.py](../../scripts/test_check_flaky_tests.py).
- Тільки workflow_dispatch, один job на одному self-hosted Linux раннері; matrix і schedule відсутні. Concurrency не допускає одночасних запусків цього експерименту.
- Checkout фіксує github.sha. На тому самому checkout виконуються п'ять повних backend pytest-прогонів і п'ять повних frontend Node test-прогонів; кожний процес запускається після завершення попереднього. PostgreSQL — окремий disposable контейнер із міграціями, як у штатному CI.
- Для Python використано окремий requirements-ci-hashes.lock: ті самі 52 точні версії, що в requirements.lock, із SHA256 wheel-файлів з офіційного PyPI release JSON. Встановлення виконується з --require-hashes і --only-binary=:all:; основний requirements.lock і штатний CI не змінені.
- Падіння тесту не зупиняє подальші повтори. Для кожного повтору зберігаються JUnit, лог, exit code, тривалість і результат кожного тесту. Порівняння виявляє зміну pass/fail/skip і зниклі тести.
- Неповний/пошкоджений звіт, помилка collection/setup або невідповідний exit code позначають експеримент неповним. Стабільні падіння наведені окремо від змінних результатів.
- summary.md і summary.json разом з усіма XML/log завантажуються одним artifact. Кандидат на нестабільність — підстава для аналізу причини; автоматичне приховування чи карантин не виконуються.

## Перевірені локальні результати

- Вісім контрактних тестів аналізатора пройшли: у тому числі справжній дочірній процес, що падає в першому повторі та виконується ще чотири рази, і п'ять інфраструктурних помилок без звіту, які не видаються за успіх.
- Повний frontend-набір з main 4f9dc53: 129 passed, JUnit успішно прочитано аналізатором. Локальний Node — v24.22.0, залежності взято з наявного checkout; workflow використовує Node 22 і npm ci із lockfile. Це допоміжна локальна перевірка, не доказ п'яти CI-прогонів.
- YAML перевірено парсером і actionlint v1.7.12: лише workflow_dispatch, один job, без matrix; вирази контекстів валідні. Кожний тестовий процес обмежено 180 секундами, 10 процесів — до 30 хв, job — до 45 хв разом із підготовкою й артефактами. Звіти ізольовані в runner.temp за run_id та run_attempt.
- Повний локальний backend-прогін наразі заблокований середовищем: доступний Python 3.12.10 не має pytest (No module named pytest); ізольований PostgreSQL для цього checkout локально не піднятий. Це не падіння прикладного тесту й не результат пошуку flakiness.

## Обов'язкові докази після запуску

Бонус ще не позначено завершеним: справжній manual run цього нового workflow не запускався. Для workflow_dispatch файл має бути в default branch; це [вимога GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

Після погодженого злиття PR:

1. Actions → Lab10 Flaky Test Check → Run workflow → main. Запустити один раз і дочекатися всіх п'яти повторів обох наборів.
2. Зберегти фактичний URL, SHA і artifact. Додати summary.md та summary.json у docs/ci-cd/evidence/bonus4/; XML/log можна додати разом або послатися на artifact і зафіксувати строк зберігання.
3. Якщо результати змінювалися — визначити причину і виправити тест або винести в карантин з issue, де названо причину. Якщо експеримент неповний — виправити інфраструктуру й повторити; він не доводить відсутності flakiness.
4. Вставити фактичні докази в розділ «Бонуси» в кінці командного dora-summary.md. Готове доповнення — [dora-summary-bonus4-fragment.md](./dora-summary-bonus4-fragment.md).
5. Пояснити реалізацію, результати й обмеження у власному Loom. Без цього пояснення бонус за умовами викладача не зараховується.
