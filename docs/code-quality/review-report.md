# Реценція на код з Лаб4 команди Next-Gen

## 3 сильні сторони :
1. **Стиль:** Назви функцій та класів прозорі та відповідають своїй суті (HealthResponse, get_listings, ListingPublicResponse). Це робить код читабельним. (Розташовано у файлах main.py та schemas/listings.py)
2. **Якість і підтримуваність:** При створенні нового оголошення система самостійно встановлює поточний час у поля created_at та updated_at за допомогою datetime.now(). (Розташовано у файлі routers/listings.py, всередині функції create_listing)
3. **Безпека:** У публічних запитах (отримання списку або конкретного оголошення) використовується модель ListingPublicResponse, яка бере всі базові дані з ListingBase, але не має поля contact. Контакти додаються лише у повній моделі ListingResponse. (Розташовано у файлі routers/listings.py та schemas/listings.py)

## 3 пропозиції покращення :
1. **Якість і підтримуваність:** У файлі з оголошеннями кілька разів повторюється один і той самий цикл for listing in MOCK_LISTINGS для пошуку конкретного запису. Краще винести цей пошук в окрему маленьку функцію, щоб не копіювати одні й ті самі рядки тексту тричі. (Розташовано у файлі routers/listings.py (get_listing, update_listing, delete_listing))
2. **Якість і підтримуваність:** Функція списку get_listings вміє видавати дані порціями (через skip та limit). Але вона віддає просто список оголошень. Фронтенду буде важко зробити кнопки "Сторінка 1, 2, 3...", бо система не каже їм загальну кількість оголошень. Варто повертати щось на зразок {"total": 100, "items": [...]}. (Розташовано у файлі routers/listings.py)
3. **Стиль і стандарти кодування:** Блок ПРИМІТКА ДЛЯ BACKEND LEAD (Данііл / @megatr4n) на самому початку main.py варто прибрати. Такому тексту місце в описі Pull Request або в загальному файлі README.md. У файлах коду подібні повідомлення швидко застарівають, засмічують простір і не несуть технічної цінності для майбутніх розробників.

## 1 знайдена потенційна вразливість або ризик:
**Безпека:** У файлі routers/listings.py маршрути для редагування (@router.patch) та видалення (@router.delete) оголошень просто шукають запис за listing_id і одразу виконують дію. Оскільки немає перевірки поточного користувача (наприклад, порівняння токена з user_id у моделі), будь-яка стороння людина може зловживати цим і безперешкодно видаляти або змінювати чужі оголошення.
