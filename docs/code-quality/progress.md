# Прогрес розробки прототипу  Lab 05

## 1. Поточний стан проєкту

**Rehab** це вебзастосунок для відстеження періоду тверезості. Він має допомагати користувачам відмічати дні без алкоголю, переглядати свій прогрес, встановлювати цілі та отримувати нагадування.

Для реалізації серверної частини використовується Python та фреймворк FastAPI.
На момент виконання лабораторної в репозиторії вже є базова реалізація API, моделі даних, маршрути календаря та цілей. Також підготовлено документацію з вимогами, архітектурою та описом API.

### Стан основних компонентів

| Компонент | Поточний стан |
|---|---|
| Структура проєкту | Створена |
| FastAPI-застосунок | Базова реалізація є |
| Календар тверезості | API-маршрути реалізовані, роботу ще потрібно перевірити |
| Цілі користувача | API-маршрути реалізовані, роботу ще потрібно перевірити |
| Моделі даних | Створені |
| Авторизація | Демонстраційна реалізація |
| База даних | Поки використовуються дані в пам'яті |
| Статистика та нагадування | Подальша реалізація |

На цьому етапі проєкт ще не є повністю готовим застосунком, але вже має основу для поступового додавання функціональності

## 2. Структура коду

Python-код розміщений у папці `src/api/`
Основні частини:

- `main.py` – створення та налаштування FastAPI-застосунку;
- `models.py` – опис моделей даних;
- `security.py` – механізми перевірки доступу;
- `errors.py` – обробка помилок;
- `stubs.py` – робота з демонстраційними даними;
- `routers/calendar.py` – маршрути для календаря;
- `routers/goals.py` – маршрути для цілей користувача.

Окрім програмного коду, у репозиторії є папки для документації, тестів і налаштувань GitHub Actions
Такий поділ дозволяє працювати над окремими частинами застосунку, не розміщуючи весь код в одному файлі.

## 3. Перевірка якості коду

Під час Lab 05 було проведено перевірку Python-коду за допомогою Black, Flake8 та Bandit.

### Black – форматування коду

Під час першої перевірки Black повідомив, що 7 Python-файлів потребують форматування.

Було виконано команду `python -m black src`, яка автоматично відформатувала ці файли.
Після повторного запуску `python -m black --check src` усі 10 перевірених файлів відповідали форматуванню Black.

### Flake8 – перевірка стилю

Початкова перевірка показала зауваження щодо довгих рядків та відсутності символу нового рядка наприкінці деяких файлів.

Після форматування Black і створення конфігураційного файлу `.flake8` перевірка `python -m flake8 src` завершилася без зауважень.

Для сумісності з Black встановлено максимальну довжину рядка 88 символів та вимкнено правила E203, W503 і E501. Відповідно, Flake8 наразі не перевіряє перевищення довжини рядків.

### Bandit – перевірка безпеки

Для пошуку потенційних проблем безпеки використано команду `python -m bandit -r src`.

Результати:

- Перевірено 638 рядків Python-коду.
- Знайдено 0 проблем низького, середнього та високого рівнів.
- Жоден файл не був пропущений.

Це позитивний результат, однак він не означає, що в застосунку гарантовано відсутні всі вразливості.

### Загальні результати

| Перевірка | Результат |
|---|---|
| Black | Успішно, 10 файлів |
| Flake8 | 0 зауважень за активними правилами |
| Bandit | 0 знайдених проблем |
| `git diff --check` | Проблем із пробілами не виявлено |

## 4. Зміни під час лабораторної

Для виконання перевірок було створено окрему гілку `feature/lab05-quality`.

Під час роботи:

- Повторно перевірено форматування та стиль коду.
- Проведено статичний аналіз безпеки.

Основні зміни стосувалися форматування та покращення узгодженості стилю коду. Нова функціональність у межах цих змін поки не додавалася.

## 5. Обмеження та наступні кроки

У Rehab уже є основа серверної частини, але деякі можливості поки залишаються демонстраційними.

Зокрема, дані зберігаються в пам'яті, а замість повноцінної авторизації використовуються тестові механізми доступу.

Наступні кроки:

1. Запустити FastAPI та перевірити роботу календаря або цілей через Swagger UI.
2. Додати автоматичні тести для основних API-маршрутів.
3. Узгодити результати аналізу безпеки з учасником, відповідальним за Security Analyst.
4. Завершити перевірку змін та створити Pull Request.
5. Продовжити розробку функціональності відповідно до вимог проєкту.
