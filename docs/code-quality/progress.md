# Прогрес розробки прототипу  Lab 05

## 1. Поточний стан проєкту

**Rehab** це вебзастосунок для відстеження періоду тверезості. Він має допомагати користувачам відмічати дні без алкоголю, переглядати свій прогрес до фіксованих етапів та отримувати нагадування.

Для реалізації серверної частини використовується Python та фреймворк FastAPI.
На момент виконання лабораторної в репозиторії вже є базова реалізація API, моделі даних, маршрути календаря та цілей. Також підготовлено документацію з вимогами, архітектурою та описом API.

Основні API-компоненти календаря та цілей були реалізовані й перевірені під час Lab 04. Тому в Lab 05 основну увагу приділено якості вже наявного коду, його форматуванню та налаштуванню автоматичних перевірок.

На цьому етапі проєкт ще не є повністю готовим застосунком, але вже має основу для поступового додавання функціональності

## 2. Структура коду

Python-код розміщений у папці `src/api/`
Основні частини:

- `main.py` – створення та налаштування FastAPI-застосунку;
- `models.py` – опис моделей даних;
- `security.py` – механізми перевірки доступу;
- `errors.py` – обробка помилок;
- `stubs.py` – робота з демонстраційними даними;
- `routers/calendar.py` – маршрути для календаря;
- `routers/goals.py` – маршрути для цілей користувача.

Окрім програмного коду, у репозиторії є папки для документації, тестів і налаштувань GitHub Actions
Такий поділ дозволяє працювати над окремими частинами застосунку, не розміщуючи весь код в одному файлі.

## 3. Робота прототипу

Основну функціональність API календаря та цілей було перевірено під час Lab 04 через Swagger UI.

Перевірялися як успішні запити, так і різні помилкові ситуації.

**Календар**

*POST* — створення запису, перевірка авторизації, заборони майбутніх дат і повторних записів.

*GET* — отримання списку записів та перевірка параметрів limit і offset.

*PATCH* — зміна запису та обробка випадку, коли запис не існує.

**Цілі**

Початкова лабораторна версія підтримувала CRUD-маршрути користувацьких цілей.
За погодженим командним рішенням поточна реалізація повертає через
`GET /api/v1/goals` фіксовані етапи на 7 і 30 днів; створення, редагування та
видалення цілей більше не підтримуються.

Отже, базові маршрути календаря та цілей були перевірені ще в попередній лабораторній. У Lab 05 ці компоненти використовуються як основа для перевірки якості коду.

**Автоматичне тестування API** (Lab 05)

Під час Lab 05 було створено файл tests/test_api.py із трьома базовими автоматичними тестами. Для їх запуску використано pytest.

**Тести перевіряють:**
- Доступність OpenAPI-документації (/openapi.json)
- Наявність маршруту календаря (/api/v1/calendar/entries)
- Наявність маршруту цілей (/api/v1/goals)
- Для запуску тестів використано команду `python -m pytest tests/test_api.py -v`.

Результат: усі 3 тести успішно пройшли (3 passed). Також було отримано одне попередження від бібліотеки Starlette, яке не вплинуло на виконання тестів.
Ці тести поки перевіряють лише базову структуру API, а не повну роботу календаря та цілей.

## 4. Перевірка якості коду

Під час Lab 05 було проведено перевірку Python-коду за допомогою Black, Flake8 та Bandit.

### Black – форматування коду

Під час першої перевірки Black повідомив, що 7 Python-файлів потребують форматування.

Було виконано команду `python -m black src`, яка автоматично відформатувала ці файли.
Після повторного запуску `python -m black --check src` усі 10 перевірених файлів відповідали форматуванню Black.

### Flake8 – перевірка стилю

Початкова перевірка показала зауваження щодо довгих рядків та відсутності символу нового рядка наприкінці деяких файлів.

Після форматування Black і створення конфігураційного файлу `.flake8` перевірка `python -m flake8 src` завершилася без зауважень.

Для сумісності з Black встановлено максимальну довжину рядка 88 символів та вимкнено правила E203, W503 і E501. Відповідно, Flake8 наразі не перевіряє перевищення довжини рядків.

### Bandit – перевірка безпеки

Для пошуку потенційних проблем безпеки використано команду `python -m bandit -r src`.

Результати:

- Перевірено 638 рядків Python-коду.
- Знайдено 0 проблем низького, середнього та високого рівнів.
- Жоден файл не був пропущений.

Це позитивний результат, однак він не означає, що в застосунку гарантовано відсутні всі вразливості.

### Gitleaks — перевірка секретів

У межах бонусного завдання Lab 05 було налаштовано pre-commit із Gitleaks для пошуку випадково доданих секретів у коді, зокрема паролів і токенів.
Для цього створено файл `.pre-commit-config.yaml` та встановлено Git hook за допомогою команди `python -m pre_commit install`.

Перевірку запущено командою `python -m pre_commit run --all-files`. Результат — `Detect hardcoded secrets...Passed`. Під час перевірки секретів не виявлено.

### pip-audit — аудит залежностей

Для перевірки сторонніх Python-бібліотек на відомі вразливості було використано pip-audit.
Перевірку виконано командою `python -m pip_audit -r requirements.txt`. Результат — `No known vulnerabilities found`, тобто відомих вразливостей у перевірених залежностях не знайдено.

Також створено GitHub Actions workflow `.github/workflows/dependency-audit.yml`, який налаштовано на перевірку залежностей під час Pull Request до `main` та після змін в основній гілці. Його роботу на GitHub ще потрібно перевірити.

## 5. Автоматизація перевірок через GitHub Actions

Щоб не запускати перевірки форматування та стилю вручну після кожної зміни коду, було додано workflow .github/workflows/code-quality.yml.

Він налаштований на автоматичний запуск Black і Flake8 під час створення Pull Request до main, а також після оновлення основної гілки.

**Workflow виконує такі дії:**
- Отримує код із репозиторію.
- Налаштовує середовище Python.
- Встановлює Black і Flake8.
- Перевіряє форматування та стиль файлів у папці src.
Якщо перевірка не проходить, GitHub Actions показує помилку, яку команда може виправити до об'єднання змін.

Локально обидві перевірки пройшли успішно. Результат запуску workflow на GitHub потрібно перевірити окремо після створення Pull Request.

### Автоматичний аудит залежностей

Додатково для Lab 05 створено workflow `.github/workflows/dependency-audit.yml`. Він використовує pip-audit для перевірки залежностей, перелічених у `requirements.txt`.

Локальна перевірка завершилася успішно: відомих вразливостей не знайдено. Сам workflow ще потрібно перевірити після його запуску на GitHub Actions.

## 7. Обмеження та наступні кроки

У Rehab уже є основа серверної частини, але деякі можливості поки залишаються демонстраційними.

Зокрема, дані зберігаються в пам'яті, а замість повноцінної авторизації використовуються тестові механізми доступу.

Наступні кроки:

1. Перевірити успішність workflow code-quality.yml та dependency-audit.yml у GitHub Actions.
2. Розширити автоматичні тести, щоб перевіряти не тільки наявність маршрутів, а й правильність відповідей API.
3. Узгодити результати аналізу безпеки з Security Analyst.
4. Завершити перевірку змін та створити Pull Request.
5. Продовжити розробку функціональності відповідно до вимог проєкту.

## 9. Прогрес розробки інтегрованого прототипу Rehab

**Дата звіту:** 15 жовтня 2026 року.

Після виконання лабораторних робіт команда продовжила розробку Rehab та підготувала інтегрований прототип із серверною і клієнтською частинами.

Розділи 1–8 описують попередній етап розробки та перевірок якості коду. Цей розділ фіксує наступний етап роботи над функціональним прототипом.

### 9.1. Структура та технології

Прототип розроблено з використанням таких технологій:

- **Backend:** Python, FastAPI, Pydantic.
- **Frontend:** React Native, Expo, Expo Router, TypeScript.
- **Тестування:** pytest, FastAPI TestClient.

Серверну частину прототипу розміщено в `backend/app/`, клієнтську — у `frontend/`.

Інтеграцію Backend та Frontend виконували в гілці `feature/rehab-prototype`.

### 9.2. Реалізована функціональність

У межах прототипу реалізовано:

- створення календарних записів зі статусами `sober` і `relapse`;
- збереження інформації про напої, їхній об'єм і коментарі;
- отримання статистики тверезості через API;
- підрахунок поточної та найдовшої серії тверезих днів;
- відстеження прогресу цілей із переходом від 7 до 30 днів;
- інтеграцію основних екранів Frontend із Backend;
- навігацію між 16 маршрутами застосунку, частина яких є демонстраційними заглушками.

Для обміну даними використовується HTTP API на FastAPI. Налаштовано CORS для взаємодії з Expo Web.

### 9.3. Перевірка прототипу

За результатами командного тестування інтегрованої версії:

- успішно пройдено 50 тестів Backend за допомогою pytest;
- перевірено створення календарних записів і валідацію даних;
- перевірено отримання статистики та розрахунок прогресу цілей;
- виконано ручну перевірку основних користувацьких сценаріїв в Expo Web.

Ці результати стосуються тестування інтегрованого прототипу і не замінюють результати перевірок, описані в попередніх розділах.

### 9.4. Обмеження

Поточна версія є демонстраційним прототипом. Дані зберігаються в оперативній пам'яті сервера, а повноцінна авторизація, постійна база даних і деякі функції інтерфейсу ще не реалізовані.

Під час встановлення залежностей Frontend також було зафіксовано попередження npm про вразливості, які потребують подальшого аналізу.
