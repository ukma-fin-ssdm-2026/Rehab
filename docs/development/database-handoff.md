# PostgreSQL — основа Поліни для інтеграції на КТ-1

## Що реалізовано

- `backend.app.db.base.Base` — спільна основа SQLAlchemy.
- `backend.app.db.session.get_db()` — сесія на запит; commit виконує маршрут/сервіс,
  при помилці виконується rollback, сесія завжди закривається.
- `backend.app.core.clock.today_local()` — дата Europe/Kyiv; `utc_now()` — UTC.
- `alembic upgrade head` і `alembic -x test_db=true upgrade head` — dev/test відповідно.
- `0001_initial` створює users, day_records та goals. Таблиця users узгоджена з полями
  моделі User з PR #172; модель цієї учасниці не скопійована й не переписана.
- `backend.app.db.models.entry.DayRecord` і календарний PostgreSQL-репозиторій.
- Локальний Compose, окремі dev/test БД та .env.example.

Наявні HTTP-маршрути календаря, статистики та цілей ще працюють із stubs.
Ця зміна не оголошує їх переведеними на PostgreSQL і не вмикає demo-токени
як виробничу авторизацію. Повне проходження КТ-1 ще потребує командної інтеграції.

Підготовлено `backend.app.routers.calendar_postgres.router` із POST/GET списку/
GET деталей/PATCH. Його HTTP-контракти перевіряються на реальній тестовій PostgreSQL
зі справжньою авторизацією Анастасії, Argon2 та JWT. Календарні контрактні
тести підміняють лише відсутній перерахунок Марії; перевірка відсутності
перерахунку окремо підтверджує 503 без запису. Старий ізольований набір
`test_calendar_postgres_api.py` зберігає явні підміни обох меж. У `main.py` він
навмисно ще не зареєстрований. Під час переходу потрібно ЗАМІНИТИ старий calendar
router, а не зареєструвати обидва на однакових шляхах.

Маршрутизатор вимагає справжній `services.progress_sync.recompute_progress`.
Якщо модуля ще немає, POST/PATCH відповідають 503 PROGRESS_SYNC_UNAVAILABLE до
запису даних; тихого пропуску перерахунку немає. Помилки вже наявного модуля
не маскуються як його відсутність. GET не залежить від перерахунку.

Після підключення нової авторизації використовувати саме її get_current_user.
Без цього перемикання окремий маршрутизатор не можна вважати готовим до публікації.

## Інтерфейс календарного репозиторію

Модуль: `backend.app.repositories.entries`.

| Функція | Результат / поведінка |
|---|---|
| create_entry(db, user_id, body: EntryCreate) | EntryOut; flush без commit; перевіряє діапазон відстеження |
| get_own_entry(db, user_id, record_id) | EntryOut; чуже й відсутнє однаково EntryNotFound |
| update_entry(db, user_id, record_id, body: EntryUpdate) | EntryOut; до 48 годин включно; дата/created_at незмінні |
| list_user_entries(db, user_id, date_from=None, date_to=None, limit=None, offset=0) | list[EntryOut]; за спаданням дати; без limit повертає всю історію |
| count_user_entries(db, user_id, date_from=None, date_to=None) | Кількість за тим самим фільтром, без пагінації |
| list_relapse_entries(db, date_from, date_to) | Записи зривів усіх акаунтів за включним діапазоном; це внутрішні дані, не готова публічна відповідь |

Репозиторії не роблять commit. Для create/update блокують рядок users до завершення
транзакції: це дає спільний порядок мутацій календаря й перерахунку статистики.
Після flush потрібно викликати справжній `recompute_progress`, тоді commit один раз.
При помилці перерахунку слід відкотити і запис, і прогрес.

Помилки для майбутнього маршруту:
- EntryNotFound → 404 ENTRY_NOT_FOUND.
- EntryEditWindowExpired → 403 EDIT_WINDOW_EXPIRED.
- EntryDateOutOfRange → 422 із поясненням допустимого діапазону.
- IntegrityError саме для uq_day_records_user_date → rollback і 409 ENTRY_ALREADY_EXISTS.
  Інші IntegrityError не маскувати під дублікат.

Тригери/напої повертаються через наявні Pydantic-схеми. Зміна на sober очищує тригер
та список напоїв, але зберігає початковий created_at.

## Анастасії

Актуальну авторизацію з develop інтегровано в робочу гілку Поліни без
переписування коду Анастасії. User використовує ту саму Base та міграцію;
тимчасове відображення таблиці users у календарній fixture прибрано.

Спільні fixtures у tests/conftest.py:
- `authenticated_calendar`: окремий тестовий app зі справжніми auth/calendar
  routes і сесіями тільки перевіреної тестової PostgreSQL. Головний app не перемикається.
- `registered_users`: два акаунти створюються через /auth/register та /auth/login;
  повертаються пари (UserPublic, заголовки зі справжнім JWT).
- `calendar_contract_api`: явно підміняє лише progress callback для контрактних
  тестів календаря. Це не підтвердження справжнього перерахунку.

Перевірені реєстрація, Argon2 у БД, me, читання власних записів, ізоляція U1/U2,
заборона demo-токенів, вихід і блокування/розблокування без відновлення старого JWT.
Для окремого тесту виходу/блокування використовується справжня PostgreSQL;
адмінський HTTP API залишається відповідальністю Софії.

Старі tests/test_security.py адаптовано до чинного контракту: справжні JWT
і User з PostgreSQL, ролі читаються з БД, нульовий sub відхиляється.
Підтримку user-42/admin-1 у код авторизації не повернуто.

## Марії

Надати Goal ORM та `recompute_progress(db, user_id, today)` без commit.
Дані календаря можна читати через list_user_entries без limit; не читати stubs.
Для мутацій цілей/перерахунку використовувати той самий порядок блокування
користувача, що й календар, щоб паралельні зміни не записували застарілий прогрес.
Не створювати нову початкову міграцію goals: таблиця вже входить у 0001_initial.

## Софії

У requirements.txt запропоновані необхідні для цього блоку SQLAlchemy/Alembic/
psycopg/python-dotenv/tzdata. Це локальний diff на перегляд; залежності авторизації
залишаються частиною узгодження PR #172. Встановлення тільки старого requirements
не забезпечує нові тести.

Для CI потрібні окремі DATABASE_URL і TEST_DATABASE_URL та PostgreSQL-сервіс.
Спочатку застосувати тестову міграцію, далі виконувати pytest. Відсутня тестова БД
є помилкою підготовки, а не причиною мовчки пропустити DB-тести.
Не логувати повний docker compose config, .env або рядки підключення з паролями.

Dev і test повинні мати різні назви БД навіть за різних host/port. Параметри query,
що перевизначають dbname/host/hostaddr/port/user/service/conninfo та облікові дані,
відхиляються. Звичайні TLS-параметри на кшталт sslmode підтримуються.

Для локального старту використати compose; для онлайн-середовища — окрему БД
з потрібними секретами. На імпорті app та при генерації OpenAPI з’єднання з БД
не відкривається. Не запускати міграції одночасно з кожного worker.

## Що ще потрібно виконати Поліні після інтеграції основи

- Разом із Софією перемкнути головний app на підготовлений PostgreSQL-router після інтеграції реального CurrentUser і справжнього перерахунку Марії.
- Перевірити на інтегрованих модулях GET деталей, доменні помилки й спільний транзакційний перерахунок.
- Календарні тести вже переведені на PostgreSQL і JWT; після появи progress_sync
  прибрати тестову підміну в наскрізних сценаріях і перевірити справжні похідні дані.
- Підключити календар, форму й деталі дня до спільного клієнта Анастасії.
- Завершити перевірки історичних/майбутніх дат і полів запиту за ТЗ.

## Перевірки цього блоку

Автоматизовані тести перевіряють конфігурацію й захист dev/test, імпорт без БД,
час Europe/Kyiv, міграцію та її повторне застосування, FK/унікальність/діапазон цілей,
збереження після нового engine, ізоляцію власників, фільтри й пагінацію,
точну межу 48 годин, паралельний дублікат та rollback невдалого запиту.
Ці перевірки не замінюють наскрізну перевірку авторизації, статистики й UI.

## Використання ШІ

## Фактична зупинка на КТ-1

Основа опублікована у PR #182 до develop. Після оновлення нашої гілки авторизацією
усі 233 серверні тести проходять після синхронізації з develop 06d78ed. Старі тести цілей/статистики
використовують справжній JWT і явні prototype-дані через fixture prototype_api.
Це регресійні перевірки старих модулів, не підтвердження їх перенесення в БД.
Числа й команди наведені у database-verification.md.

Підготовлено CI для develop: PostgreSQL 16, міграції тестової БД та повний
pytest. Перевірки якості й простежуваності також запускаються для develop.
На self-hosted Linux runner потрібен Docker для PostgreSQL service.

Ще потрібні справжній progress_sync/Goal Марії, підключення маршрутів і онлайн
від Софії, командна перевірка і review Марії для PR Поліни. Умова виходу КТ-1
(розділ 11.3 ТЗ) ще не виконана. UI календаря до КТ-2 не оголошується готовим.

## Оновлений стан після злиття PR #182

Станом на 29.10.2026 `recompute_progress` Марії та ORM-модель і репозиторій
Goal інтегровані. Маршрути цілей і статистики працюють із PostgreSQL; календарні
POST/PATCH викликають перерахунок у тій самій транзакції. Зміни цілей,
статистики й календаря серіалізуються блокуванням рядка користувача.

Перевірка гілки Марії на актуальному develop: `python -m pytest -q` —
**253 passed**, одне попередження Starlette щодо httpx. Окрема перевірка
`tests/test_progress_sync_calendar.py` підтверджує, що запис дня оновлює
прогрес цілі через реальний календарний PostgreSQL-router.

Залишилося підключити `calendar_postgres.router` замість prototype-router
у `main.py` та виконати наскрізну інтеграцію календаря й онлайн-сценарії.
Це суміжна командна робота; до її завершення цей документ не оголошує всю
контрольну точку КТ-1 закритою.

## Уточнення контракту етапів після командного погодження

Поточна поведінка застосунку використовує фіксовані етапи на 7 і 30 днів.
`GET /api/v1/goals` повертає їхній стан, обчислений із календарної історії;
користувацькі операції створення, зміни та видалення відсутні. Таблиця `goals`
залишається в схемі як частина міграції `0001_initial` для сумісності, але код
застосунку її записи не читає й не змінює. Усі нові функціональні тести мають
використовувати лише тестову БД.
