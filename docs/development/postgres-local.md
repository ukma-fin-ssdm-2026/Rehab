# Локальна PostgreSQL для Rehab

Усі команди виконуються з кореня локального репозиторію Rehab.
Потрібні запущений Docker Desktop із Linux-рушієм та Docker Compose.

## Перше налаштування

1. Скопіювати `.env.example` у `.env`.
2. Задати два різні випадкові паролі та вказати ті самі значення у відповідних URL.
3. Запустити бази:

```powershell
docker compose up -d --wait
docker compose ps
```

На підготовленому комп’ютері `.env` уже створений із випадковими паролями.
Його не потрібно перезаписувати: пароль у наявному PostgreSQL volume не змінюється
простим редагуванням `.env`. Сам `.env` виключений із Git.

| Призначення | Сервіс | База й користувач | Адреса на комп’ютері |
|---|---|---|---|
| Розробка | postgres-dev | rehab_dev | 127.0.0.1:25432 |
| Автоматизовані тести | postgres-test | rehab_test | 127.0.0.1:25433 |

Порти відрізняються від стандартного 5432, щоб не зачіпати PostgreSQL інших проєктів.
Для підключення з Python на комп’ютері використовуються DATABASE_URL і TEST_DATABASE_URL
із `.env`. Паролі й рядки підключення не потрібно надсилати в PR або командний чат.

## Перевірка з’єднань

```powershell
docker compose exec -T postgres-dev psql -U rehab_dev -d rehab_dev -c "SELECT current_database();"
docker compose exec -T postgres-test psql -U rehab_test -d rehab_test -c "SELECT current_database();"
```

Очікувані значення: rehab_dev та rehab_test відповідно.
Тестові сценарії повинні працювати тільки з TEST_DATABASE_URL.

## Зупинка й повторний запуск

```powershell
docker compose stop
docker compose start
```

Кожен сервіс має власний постійний Docker volume; звичайна зупинка зберігає дані.
Не запускати `docker compose down -v`, якщо потрібно зберегти дані: прапорець `-v`
видаляє volumes.

## Робоче сховище

Усі робочі HTTP-модулі використовують PostgreSQL; дані й фото не скидаються після перезапуску API. Онлайн-БД Neon та локальні dev/test середовища незалежні. Схема керується Alembic, поточний head — 0002_team_foundation.

## Міграції та перевірки

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic -x test_db=true upgrade head
.\.venv\Scripts\python.exe -m pytest -q
```

Перша міграційна команда використовує DATABASE_URL; друга — TEST_DATABASE_URL.
Тестова адреса обов’язкова, повинна вказувати на іншу БД із назвою, що закінчується
на `_test`. Відмінного пароля для тієї самої адреси/бази недостатньо.
Бази для розробки й тестів ніколи не підмінюються одна одною.

Тести PostgreSQL не пропускаються автоматично за відсутності налаштувань:
для їхнього виконання потрібен запущений test-сервіс. Фікстура календарних тестів
очищує лише перевірену тестову БД, не dev-БД.

Повторний `upgrade head` зберігає дані. Нову міграцію створюють лише для погодженої зміни схеми з усіма ORM-моделями в metadata; її переглядають перед застосуванням. Уже застосовані міграції не переписуються. Звичайний запуск API не створює, не скидає й не засіває схему автоматично.
