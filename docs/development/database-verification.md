> Історія локальних перевірок основи БД до завершення КТ1. Зазначені нижче
> майбутні інтеграції та особисті цілі описують відповідні проміжні коміти.
> Поточний контракт: [database-handoff.md](database-handoff.md);
> онлайн-приймання: [calendar-kt2.md](../validation/calendar-kt2.md).

Локальна перевірка у Windows, Python 3.12, PostgreSQL 16.14, окремі rehab_dev/rehab_test.
Це результати локального запуску, а не GitHub Actions або публічного розгортання.

Міграція `upgrade head` виконана для обох локальних БД. Повторне застосування,
унікальність дати, FK та діапазон цілей перевіряються тестами на PostgreSQL.
Календарні перевірки включають нове з’єднання замість спільного in-memory стану,
конкурентний дублікат, точну межу 48 годин, власників та rollback запису й похідних
змін у разі помилки перерахунку.

Під час незалежного огляду додатково перевірена безпека адреси тестової БД.
Потенційне перевизначення цілі через query-параметри psycopg усунуте;
регресійні тести перевіряють відхилення таких параметрів і різні назви dev/test.
Після виправлення важливих зауважень до цього блоку огляд не виявив.

## Підготовка основи до злиття

Після адаптації застарілих тестів **226 passed**, одне попередження
Starlette/httpx; окремий валідатор — **4 passed**. Повний набір не має
пропущених або видалених через несумісність тестів. Застосовано форматування
авторизації Анастасії з PR #178, без зміни її логіки.

Цілі й статистика в старих регресійних сценаріях залишаються на явних stubs;
новий prototype_api використовує справжні акаунти й JWT із тестової PostgreSQL.
Це усуває несумісність auth, але не підміняє майбутню реалізацію Марії.
У security-тестах попереднє прийняття нульового user_id замінено перевіркою
його відхилення за погодженим JWT-контрактом.

CI Pipeline тепер запускається для develop з PostgreSQL 16, динамічним портом,
різними назвами dev/test та явною тестовою міграцією перед pytest. Повторний
непідготовлений запуск pytest із Code Quality прибрано: повний набір із
покриттям належить CI Pipeline, у тому числі для старої feature/rehab-prototype.
Code Quality та Lab07 Traceability також охоплюють develop. Синтаксис трьох
YAML-файлів локально розібрано; фактичний успіх GitHub Actions перевіряється
окремо після push і не випливає з локального прогону.

Black усіх backend і змінених тестів, Flake8, pip check, diff check та
простежуваність пройшли. Незалежний огляд важливих/критичних зауважень не має.
КТ-1 усієї системи ще не підтверджена: справжній progress/Goal, підключення
router, admin та онлайн-сценарії залишаються командними залежностями.

## Проміжний прогін після інтеграції авторизації з develop

Гілку Поліни оновлено з develop 01d9a36, локальний merge 637db66; спільні
develop/main не змінювалися. Новий прогін загального набору: **194 passed,
32 failed**, одне попередження Starlette/httpx. Попередні 172 passed вище —
результат початкового коміту 86dd4a5 до інтеграції авторизації.

На цьому проміжному прогоні помилки належали старим tests/test_goals.py (11),
tests/test_statistics.py (11), tests/test_security.py (10): вони ще
використовують demo-токени або стару сигнатуру auth. Їх не видалено і не
пропущено. Потрібне узгоджене оновлення власницями модулів; загальний CI
ще не можна вважати зеленим.

Календарні сценарії tests/test_calendar.py та test_entry_details.py збережені
та адаптовані до PostgreSQL і справжніх JWT. test_calendar_auth_postgres.py
додає 10 перевірок реальної авторизації/БД; без підміни auth. Для успішних
POST/PATCH контрактний набір явно підміняє тільки відсутній progress callback.
Це не доказ коректності справжнього перерахунку Марії. Окремо перевірено
відмову 503 без збереження за відсутності справжнього progress_sync.

Вибраний набір нашої частини: **83 passed**, одне попередження Starlette/httpx.
Команда:

```powershell
python -m pytest tests/test_calendar.py tests/test_entry_details.py tests/test_calendar_auth_postgres.py tests/test_calendar_postgres_api.py tests/test_calendar_schema_contract.py tests/test_database_config.py tests/test_database_migrations.py tests/test_postgres_entries.py -q
```

Black/Flake8 змінених тестів, pip check, git diff --check та 4 тести
валідатора простежуваності пройшли. Незалежний огляд змінених fixtures і тестів
не виявив важливих/критичних зауважень.

Порядок запуску unit auth → calendar також перевірений: **21 passed**.
Виправлено успадкування тимчасових fake imports між наборами тестів: справжній
auth router завантажується до підмін unit-тестів, без підключення до БД.

## Як повторити

Запустити PostgreSQL за [postgres-local.md](postgres-local.md), установити
актуальний requirements.txt та виконати:

```powershell
python -m alembic upgrade head
python -m alembic -x test_db=true upgrade head
python -m pytest -q --cov=backend.app.core --cov=backend.app.db --cov=backend.app.repositories --cov=backend.app.routers.calendar_postgres --cov-report=term-missing
python -m pytest scripts/test_check_traceability.py -q
python scripts/check_traceability.py
```

## Що цим ще не підтверджено

- Головний app усе ще реєструє старі prototype-маршрути.
- Новий PostgreSQL-router тестується в окремому FastAPI app зі справжньою
  авторизацією. Основний app, реальний progress і публічне середовище разом
  ще не перевірені.
- Реальний recompute_progress Марії ще не інтегровано. За його відсутності новий
  router відхиляє записи з 503, а не зберігає дані без оновлення статистики.
- Повна вебзбірка, телефон і зовнішнє розгортання цього блоку ще не перевірені.

До злиття потрібна спільна перевірка КТ-1 за
[database-handoff.md](database-handoff.md).
