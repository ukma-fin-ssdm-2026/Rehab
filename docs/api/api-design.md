# Документація проєктування API — «Рехаб»

## Огляд архітектури

- **Базова адреса:** `http://127.0.0.1:8000/api/v1`
- **Стиль API:** REST
- **Підхід до проєктування:** Code-First
- **Фреймворк:** FastAPI
- **Автентифікація:** Bearer-токени; підписані JWT з актуальною перевіркою акаунта в PostgreSQL
- **Формат обміну даними:** JSON
- **Стратегія версіонування:** версія API в шляху URL (`/api/v1`)
- **Документація API:** OpenAPI / Swagger UI
- **Архітектурний стиль backend:** Layered Monolith
- **Сховище даних:** PostgreSQL через SQLAlchemy/Alembic; production-дані не підміняються in-memory stubs

API застосунку **«Рехаб»** призначений для взаємодії клієнтської частини системи із серверною логікою.

У межах поточної реалізації основна функціональність API зосереджена на таких ресурсах:

- щоденних відмітках користувача про стан тверезості (`DayRecord`);
- фіксованих етапах тверезості 7, 30, 90, 180 і 365 днів (`GoalMilestoneOut`);
- приватному профілі, його налаштуваннях і фото (`ProfileOut`);
- приватних повідомленнях та коментарях підтримки (`NotificationOut`, `SupportCommentOut`).

Специфікація OpenAPI генерується автоматично FastAPI на основі реалізованих маршрутів, Pydantic-схем, параметрів і моделей відповідей.

---

## Модель ресурсів

### Ресурс User

Ресурс `User` представляє користувача системи та використовується як власник персональних ресурсів.

У поточній лабораторній роботі окремі CRUD endpoint-и для керування користувачами не реалізовані. Ідентифікатор та роль користувача визначаються з тестового Bearer-токена.

- **Окрема кінцева точка:** у поточній версії не реалізована
- **Призначення:** ідентифікація власника персональних ресурсів та визначення його ролі
- **Основні атрибути, що використовуються API:**
  - `user_id` (integer): унікальний ідентифікатор користувача;
  - `role` (enum): роль користувача — `user`, `mentor` або `admin`.

**Зв'язки:**

- користувач може мати багато записів `DayRecord`;
- стани фіксованих етапів обчислюються з `DayRecord` для поточного користувача;
- користувацькі записи таблиці `goals` не створюються й не використовуються API.

> **Примітка щодо ролей:** механізм JWT-stub розпізнає ролі `user`, `mentor` та `admin`, однак окремі endpoint-и та бізнес-операції для ролей `mentor` і `admin` ще не реалізовані. Поточний API реалізує користувацькі сценарії Calendar, Goals і Statistics.

---

### Ресурс DayRecord

- **Кінцева точка:** `/calendar/entries`
- **Опис:** щоденна відмітка користувача про стан тверезості.

**Атрибути:**

- `record_id` (integer): унікальний ідентифікатор запису;
- `user_id` (integer): ідентифікатор власника запису;
- `date` (date): дата відмітки у форматі `YYYY-MM-DD`;
- `status` (enum): статус дня — `sober` або `relapse`;
- `trigger_category` (enum, nullable): категорія тригера зриву;
- `created_at` (datetime): дата та час створення запису.

Можливі значення `trigger_category`:

- `stress`;
- `holiday`;
- `social`;
- `other`.

**Зв'язки:**

- кожен `DayRecord` належить одному користувачу;
- один користувач може мати багато записів `DayRecord`.

**Основні бізнес-правила:**

- не можна створювати відмітки на майбутню дату;
- один користувач може мати лише одну відмітку на конкретну дату;
- `trigger_category` можна вказувати лише для `status=relapse`;
- для `status=sober` поле `trigger_category` повинно бути відсутнім або мати значення `null`;
- редагування запису дозволено лише протягом 48 годин від моменту його створення;
- дата існуючого запису під час редагування не змінюється.

---

### Фіксовані етапи тверезості

`GET /goals` повертає етапи на 7, 30, 90, 180 і 365 днів та їхній прогрес для поточного
користувача. Етап вважається виконаним, якщо його досягла найкраща серія;
прогрес активного етапу обчислюється за поточною серією. Створення,
редагування та видалення цілей користувачем не підтримуються. Таблиця `goals`
збережена лише для сумісності з початковою міграцією.

## Реалізовані endpoint-и

Наведені нижче маршрути описують календар і фіксовані етапи тверезості.

| Метод    | Endpoint                               | Призначення              |
| -------- | -------------------------------------- | ------------------------ |
| `POST`   | `/api/v1/calendar/entries`             | Створити відмітку дня    |
| `GET`    | `/api/v1/calendar/entries`             | Отримати список відміток |
| `PATCH`  | `/api/v1/calendar/entries/{record_id}` | Змінити відмітку         |
| `GET`    | `/api/v1/goals`                        | Отримати фіксовані етапи |

## Calendar API

### POST `/api/v1/calendar/entries`

Створює щоденну відмітку поточного користувача.

Приклад тверезого дня:

```json
{
  "date": "2026-10-07",
  "status": "sober"
}
```

Приклад фіксації зриву:

```json
{
  "date": "2026-10-07",
  "status": "relapse",
  "trigger_category": "stress"
}
```

Основні HTTP-статуси:

| Статус                     | Значення                            |
| -------------------------- | ----------------------------------- |
| `201 Created`              | запис успішно створено              |
| `401 Unauthorized`         | відсутня або некоректна авторизація |
| `409 Conflict`             | запис на цю дату вже існує          |
| `422 Unprocessable Entity` | помилка валідації вхідних даних     |

Після успішного створення ресурсу сервер повертає заголовок `Location` з адресою створеного ресурсу.

---

### GET `/api/v1/calendar/entries`

Повертає список відміток поточного користувача.

Endpoint підтримує:

- фільтрацію за датами;
- пагінацію через `limit` та `offset`.

Структура відповіді `EntryList` містить:

- `items` — записи поточної сторінки;
- `total` — загальну кількість записів за заданим фільтром;
- `limit` — розмір сторінки;
- `offset` — зміщення від початку результатів.

API повертає лише записи поточного авторизованого користувача.

---

### PATCH `/api/v1/calendar/entries/{record_id}`

Змінює існуючу відмітку дня.

Під час редагування можна змінити статус та пов'язану з ним категорію тригера.

Дата запису не змінюється.

Редагування дозволено лише протягом **48 годин від моменту створення запису**.

Основні HTTP-статуси:

| Статус                     | Значення                                             |
| -------------------------- | ---------------------------------------------------- |
| `200 OK`                   | запис успішно змінено                                |
| `401 Unauthorized`         | користувач не авторизований                          |
| `403 Forbidden`            | 48-годинне вікно редагування минуло                  |
| `404 Not Found`            | запис не існує або не належить поточному користувачу |
| `422 Unprocessable Entity` | некоректні вхідні дані                               |

---

## Goals API

### GET `/api/v1/goals`

Повертає фіксовані етапи 7, 30, 90, 180 і 365 днів для авторизованого користувача. Відповідь
містить `target_days`, `is_achieved` і `progress_days` для кожного етапу.
Якщо календарна історія відсутня, етап 7 є активним із прогресом 0, а етап 30
показаний як наступний. Усі етапи позначаються виконаними лише після досягнення
найкращою серією 30 днів. Запити `POST`, `PUT` і `DELETE` не підтримуються.

# Проєктні рішення

## Чому Code-First?

Для API застосунку «Рехаб» обрано підхід **Code-First**.

Основні причини:

- OpenAPI-документація генерується безпосередньо з реалізації;
- Pydantic-схеми визначають структуру запитів та відповідей;
- зменшується ризик розбіжностей між кодом та API-документацією;
- зміни моделей автоматично відображаються в OpenAPI;
- FastAPI автоматично формує Swagger UI;
- не потрібно вручну підтримувати окремий YAML-файл специфікації під час розробки.

---

## Стратегія версіонування

Використовується версіонування API через URL.

Поточна версія:

```text
/api/v1
```

Наприклад:

```text
/api/v1/calendar/entries
/api/v1/goals
```

У разі появи несумісних змін може бути створена нова версія API, наприклад `/api/v2`.

Такий підхід дозволяє розвивати API без порушення роботи клієнтів, які використовують попередню версію контракту.

---

## Стратегія пагінації

Для списку записів календаря використовується **offset-based pagination**.

Основні параметри:

- `limit` — максимальна кількість записів у поточній відповіді;
- `offset` — кількість записів, які потрібно пропустити від початку вибірки.

Відповідь містить метадані:

- `items`;
- `total`;
- `limit`;
- `offset`.

Приклад структури:

```json
{
  "items": [],
  "total": 2,
  "limit": 30,
  "offset": 0
}
```

Offset-based pagination обрана через простоту реалізації та достатність для поточного обсягу даних і навчальної версії API.

---

## Обробка помилок

Для API використовується єдина структура відповіді з помилкою — `ErrorResponse`.

Загальний формат:

```json
{
  "code": "ERROR_CODE",
  "message": "Опис помилки",
  "details": null
}
```

Поля:

- `code` — машинозчитуваний код помилки;
- `message` — зрозуміле людині пояснення;
- `details` — додаткова інформація або `null`.

Для помилок валідації `details` може містити перелік проблемних полів.

Приклад:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Помилка валідації вхідних даних",
  "details": [
    {
      "field": "body",
      "message": "Value error, trigger_category можна вказувати лише для status=relapse",
      "type": "value_error"
    }
  ]
}
```

Приклад помилки авторизації:

```json
{
  "code": "UNAUTHORIZED",
  "message": "Відсутній заголовок Authorization: Bearer <token>",
  "details": null
}
```

Приклад завершення дозволеного часу редагування:

```json
{
  "code": "EDIT_WINDOW_EXPIRED",
  "message": "Час на редагування цього запису минув (48 годин)",
  "details": null
}
```

Основні HTTP-коди API:

| Код   | Значення             | Використання                                    |
| ----- | -------------------- | ----------------------------------------------- |
| `200` | OK                   | успішне отримання або оновлення                 |
| `201` | Created              | успішне створення ресурсу                       |
| `204` | No Content           | успішне видалення                               |
| `401` | Unauthorized         | відсутня або некоректна авторизація             |
| `403` | Forbidden            | операція заборонена бізнес-правилами            |
| `404` | Not Found            | ресурс не знайдений або недоступний користувачу |
| `409` | Conflict             | конфлікт із поточним станом ресурсу             |
| `422` | Unprocessable Entity | помилка валідації                               |

---

## Авторизація та контроль доступу

Для захищених endpoint-ів використовується схема **HTTP Bearer**.

Формат:

```text
Authorization: Bearer <token>
```

У поточній лабораторній реалізації використовується **JWT-stub**, а не повноцінний JWT-механізм.

Тестовий токен має формат:

```text
<role>-<user_id>
```

Приклади:

```text
user-42
mentor-7
admin-1
```

Механізм дозволяє визначити:

- роль користувача;
- `user_id` поточного користувача.

Відсутній або некоректний токен призводить до `401 Unauthorized`.

Для персональних ресурсів додатково перевіряється їх власник.

Якщо користувач намагається отримати ресурс, який йому не належить, API повертає `404 Not Found`, а не інформацію про існування чужого ресурсу.

### Поточний стан рольового функціоналу

Механізм авторизації вже розпізнає ролі:

- `user`;
- `mentor`;
- `admin`.

Проте **окремий функціонал для ролей `mentor` та `admin` у поточній лабораторній реалізації ще не реалізований**.

На цьому етапі API зосереджений на користувацьких сценаріях:

- Calendar;
- Goals.

Таким чином, підтримка `mentor` та `admin` у JWT-stub створює основу для майбутнього рольового контролю доступу, але не означає, що окремі адміністративні або менторські endpoint-и вже існують.

---

## Вибір HTTP-методів

Для створення ресурсів використовується `POST`.

Для читання ресурсів використовується `GET`.

Для редагування `DayRecord` використовується `PATCH`, оскільки змінюється лише частина існуючого ресурсу, а дата запису залишається незмінною.

Ресурс фіксованих етапів підтримує лише читання через `GET`.

---

## Pydantic-схеми

Для визначення структури даних та їх валідації використовуються Pydantic-схеми.

Основні схеми:

- `DayStatus` — статус дня;
- `TriggerCategory` — категорія тригера;
- `EntryCreate` — створення відмітки;
- `EntryUpdate` — редагування відмітки;
- `EntryOut` — представлення відмітки у відповіді;
- `EntryList` — список відміток із метаданими пагінації;
- `GoalList` і `GoalMilestoneOut` — фіксовані етапи та їхній прогрес;
- `ErrorResponse` — єдиний формат помилки.

Pydantic-валідація забезпечує, зокрема:

- перевірку формату дат;
- заборону майбутньої дати;
- перевірку допустимих статусів;
- перевірку категорій тригерів;
- заборону `trigger_category` для `status=sober`;
- етапи 7, 30, 90, 180 і 365 днів задаються застосунком і не надходять від клієнта.

---

## OpenAPI та Swagger

Специфікація OpenAPI генерується FastAPI автоматично.

Під час локального запуску доступні:

```text
Swagger UI:
http://127.0.0.1:8000/docs

OpenAPI JSON:
http://127.0.0.1:8000/openapi.json
```

Swagger UI дозволяє:

- переглядати всі endpoint-и;
- переглядати параметри запитів;
- переглядати request/response schemas;
- переглядати можливі HTTP-статуси;
- виконувати Bearer-авторизацію;
- виконувати тестові API-запити.

Для моделей `EntryCreate` та `EntryUpdate` задані коректні OpenAPI-приклади, які не суперечать бізнес-правилу щодо `trigger_category`.

## Перевірені сценарії

Реалізований API було вручну перевірено через Swagger UI.

Перевірено такі сценарії:

1. `GET /calendar/entries` — отримання календаря авторизованого користувача (`200`);
2. `POST /calendar/entries` — створення тверезого дня (`201`);
3. повторне створення запису на ту саму дату (`409`);
4. створення запису на майбутню дату (`422`);
5. передавання `trigger_category` для `status=sober` (`422`);
6. редагування запису після завершення 48-годинного вікна (`403`);
7. редагування доступного запису (`200`);
8. звернення до неіснуючого запису (`404`);
9. отримання фіксованих етапів 7, 30, 90, 180 і 365 днів (`200`);
10. відсутність календарної історії не показує хибне повідомлення про виконання всіх етапів;
11. запити на створення, оновлення та видалення цілі не підтримуються;
14. запит без авторизації (`401`);
15. спроба іншого користувача отримати чужий ресурс (`404`).

Також окремо перевірено уніфікований формат `ErrorResponse` для помилок:

- `401 Unauthorized`;
- `403 Forbidden`;
- `404 Not Found`;
- `409 Conflict`;
- `422 Unprocessable Entity`.

## Обмеження поточної реалізації

Поточна версія API є лабораторною реалізацією.

### In-memory сховище

Архітектура системи передбачає використання **PostgreSQL**, однак у межах поточної лабораторної реалізації використовується **in-memory сховище з тестовими даними**.

Це дозволяє реалізувати та перевірити REST-контракт і бізнес-правила без підключення постійної бази даних.

### JWT-stub

Повноцінний механізм створення, підпису, перевірки та оновлення JWT у поточній версії не реалізований.

Замість нього використовується JWT-stub із тестовими токенами формату:

```text
<role>-<user_id>
```

### Ролі mentor та admin

Механізм авторизації розпізнає ролі `mentor` та `admin`, однак **окремі endpoint-и та бізнес-сценарії для цих ролей ще не реалізовані**.

Поточна реалізація охоплює користувацькі сценарії Calendar та Goals.

У наступних версіях API можуть бути додані окремі операції для ментора та адміністратора.

### Постійне зберігання даних

Оскільки використовується in-memory сховище, дані поточної лабораторної реалізації не є постійними та можуть бути скинуті після перезапуску застосунку.

У повній реалізації цей механізм має бути замінений на шар доступу до PostgreSQL.

## Підсумок

У поточній версії спроєктовано та реалізовано REST API для основних користувацьких сценаріїв застосунку «Рехаб».

API має:

- версіонування через `/api/v1`;
- JSON як формат обміну даними;
- Code-First підхід;
- автоматичну OpenAPI/Swagger-документацію;
- Bearer-авторизацію з JWT-stub;
- перевірку власника персональних ресурсів;
- Pydantic-валідацію;
- єдиний формат `ErrorResponse`;
- offset-based pagination;
- бізнес-правила Calendar;
- читання фіксованих етапів Goals;
- окремий маршрут перегляду фіксованих етапів.

Поточна реалізація створює основу для подальшого підключення PostgreSQL, повноцінної JWT-автентифікації та реалізації окремого функціоналу для ролей `mentor` та `admin`.


## Контракти повідомлень ТЗ-3 — підготовка до КТ-А

schemas/notifications.py визначає NotificationOut, SupportCommentOut, SupportCommentCreate, NotificationList і UnreadCount; frontend/src/api/notifications.ts відображає ті самі DTO. Notification та profile routers підключені до головного app після спільної ORM-основи; календар викликає подію у тій самій транзакції. Онлайн-розгортання цього стану ще має пройти командну перевірку. Відсутність маршруту не підміняється фіктивною відповіддю. OpenAPI інтегрованого застосунку й загальні tags/опис main.py оновлює Софія при інтеграції.
