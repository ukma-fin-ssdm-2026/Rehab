# Тест-план: «Рехаб» (Rehab)

## Обсяг

**Тестуємо:**
- Календар відміток (US-001): відмітка поточного дня, заборона вибору майбутньої дати
- Сповіщення ментора про зрив (US-002)
- Цілі тверезості та бейджі (US-003)
- Модерація скарг адміністратором (US-004)
- Порівняння серії з рекордом (US-005)
- Аналітика категорій тригерів (US-006)
- Редагування запису протягом 48 годин (US-007)
- Менторство за кодом (US-008)

**Свідомо НЕ тестуємо:** платіжні сервіси, медичні консультації, інтеграції з фітнес-пристроями, повне кросплатформне UI-тестування та візуальні деталі дизайну. Цільові UI-сценарії з вимог залишаються в межах плану

## Критерії виходу

- Усі наявні автоматизовані тести проходять у CI; результати системних, приймальних та нефункціональних перевірок фіксуються окремо
- Ціль покриття Backend — не нижче 95%. Історичний звіт Лаб 6 з 99% належить прототипу, поточне покриття визначається CI конкретного SHA. Поріг `--cov-fail-under=95` та перевірка гілок `--cov-branch` ще не налаштовані в CI
- Кожна FR та NFR з requirements.md має відповідний тест-кейс у плані та зв'язок у RTM. Для завершення тестування результати виконаних перевірок мають бути зафіксовані
- Навантажувальний тест (`locust` або `k6`) виконано й p95 ≤ 500 мс при 100 користувачах
- Немає відкритих критичних дефектів.

## Ризики

1. **Модерація та закриття доступу до підопічного (US-004)**: помилка дає користувачу доступ після завершення зв’язку, найвища ціна.
2. **Сповіщення про зрив (US-002)**: ментор не дізнається вчасно про кризу підопічного.
3. **Межа 48 годин (US-007)**: класичне граничне значення, легко помилитися на ±1 годину.
4. **Рекорд і серія (US-005)** та підрахунок тверезих днів: помилки на межах періоду (раніше вже був дефект `count_sober_days()` на останньому дні).
5. **Пошта та мобільний браузер:** автоматичні тести не підтверджують справжню Gmail-доставку або Safari.

## Запуск перевірок і CI

- Backend: `.github/workflows/ci.yml` запускає pytest і створює HTML-звіт покриття
- Модульні та інтеграційні тести: автоматизований запуск через pytest
- Системні та приймальні тести: перевірка сценаріїв через API або UI з окремою фіксацією результатів
- Навантажувальні тести №18 і №30: запланований запуск через Locust або k6, 100 одночасних користувачів, p95 ≤ 500 мс
- Тест №28: місячний моніторинг доступності, критерій uptime ≥ 99,5%

Поточний CI не запускає UI-, навантажувальні та місячні моніторингові перевірки. Заплановані сценарії не вважаються виконаними без результатів запуску.

### Бонус №4. Історичний нефункціональний тест продуктивності

**Вимога:** `PERF-001` — 95-й процентиль часу відповіді (p95) не повинен перевищувати 500 мс при 100 одночасних користувачах.

**Тестований компонент:** API статистики `GET /api/v1/statistics`.

**Інструмент:** Locust 2.47.0.

**Реалізація:** `tests/performance/locustfile.py`.

Тест імітує 100 віртуальних користувачів, які надсилають авторизовані запити до API статистики. Після завершення автоматично перевіряються поріг p95 та кількість помилок. Якщо поріг перевищено або є невдалі запити, тест завершується з кодом помилки.

**Команда запуску:**

```powershell
python -m locust -f tests/performance/locustfile.py --headless --host http://127.0.0.1:8000 --users 100 --spawn-rate 50 --run-time 30s
```

**Результати локального тестування (28.10.2026):**

| Показник | Значення |
|---|---|
| Віртуальні користувачі | 100 |
| Тривалість | 30 секунд |
| Кількість запитів | 1970 |
| Помилки | 0 |
| Виміряний p95 | 32 мс |
| Граничний p95 | 500 мс |
| Результат | Успішно |

**Межі:** це запуск старого прототипу з demo-токеном user-42. Чинний сервер вимагає JWT; цей скрипт потребує адаптації до нового входу перед повторним вимірюванням. Заплановані 5 хвилин у кейсах №18/30 не підміняються історичними 30 секундами.

**Висновок:** під час 30-секундної локальної перевірки з 100 віртуальними користувачами виміряний p95 становив 32 мс, що відповідає заданому порогу. Усі 1970 запитів виконалися без помилок. Locust завершив роботу з кодом `0`.
**Доказ реалізації:** [PR №159 — навантажувальний тест статистики PERF-001](https://github.com/ukma-fin-ssdm-2026/Rehab/pull/159).

## Приймання інтегрованої версії

Автоматичні сценарії використовують справжній FastAPI, JWT і окрему PostgreSQL test-БД. tests/test_system_integration.py, test_calendar_message_flow.py та test_calendar_relapse_notifications.py перевіряють наскрізні зв’язки модулів. Тести пошти використовують підмінний sender без реальних листів.

За збереженим командним протоколом від 31.10.2026 перед змінами стилів пройшли 460 backend-тестів (coverage 94%) і 85 frontend-тестів; після змін стилів — 463 backend (93%) і 90 frontend. Це попередні результати, а не новий прогін або підтвердження поточного онлайн-SHA. Результат для релізного коміту береться з його CI. Історичні лабораторні виміри нижче/вище не є поточними метриками.

Перед перенесенням у main перевіряються:

1. Реєстрація → вхід → onboarding/reload → /me; вихід, зміна пароля й відмова старому JWT.
2. Профіль: ім’я, нікнейм, стиль, opt-in пошти, фото JPEG/PNG/WebP/HEIC/AVIF і збереження після повторного входу.
3. Код → активний зв’язок → sober/relapse → головна/статистика/п’ять цілей без ручного reload; межі редагування 48 годин і збереження після перезапуску API.
4. Один зрив → одне повідомлення → один коментар → скарга з доказом → рішення адміністратора → закритий доступ, працездатний власний акаунт і заборона повторної пари.
5. Виправлення на sober, повторний relapse, відсутність ментора під час першої події, ізоляція акаунтів та історія після завершення.
6. Job після 20:00 Kyiv: opt-in/off, явний запис, повтор без дубля; окремо реальне отримання Gmail і оновлення access token після OAuth.
7. /health, /ready, прямі посилання й reload, холодний старт, доступність без ноутбуків команди.
8. На справжньому iPhone/Safari: форми, навігація, фото з галереї, попередження/скасування стилю, зміна тексту після нового входу, прямі URL. Зафіксувати модель, iOS, дату, SHA backend/frontend і фактичний результат.

Попередньо команда перевіряла iPhone 16 Pro Max / iOS 18.3.2; це не підтверджує новий реліз. Android не входить до погодженого мобільного приймання; додаткові перевірки фіксуються окремо.
