## Захист тестової БД

Тільки **одноразова ізольована PostgreSQL**, не production Neon і не база
розробки зі справжніми людьми. Встановити локальні `DATABASE_URL` і
`TEST_DATABASE_URL` у середовищі; URL мають вказувати на **різні бази**,
а ім'я тестової закінчуватися на `_test`. Тестова фікстура перевіряє
ці умови перед операціями та очищає тестові дані через TRUNCATE CASCADE.
Не вставляти ці URL, JWT або паролі в PR, скриншоти, логи чи чат.

Запуск із кореня Rehab:

```powershell
python -m pip install -r requirements.txt
python -m alembic heads
python -m alembic -x test_db=true upgrade head
python -m pytest -q tests/test_profile_postgres_integration.py
python -m pytest -q tests/test_profile_contract.py tests/test_profile_service.py tests/test_profile_routes.py tests/test_avatar_image.py
python -m pytest -q
```

Фікстура реєструє **справжні** `auth.router` і `profile.router` у
приватному FastAPI test-app. JWT підписаний, `get_current_user` не
замінено моками, запити йдуть до реальної SQLAlchemy Session. Усі адреси
акаунтів синтетичні в домені `*.test`.

## Сценарії автоматичних HTTP-тестів

1. Гість отримує 401. Два користувачі бачать лише власний профіль;
   зайві поля `email`, `role`, `user_id`, `mentor_code` відхиляються.
   Ім'я/нікнейм нормалізуються, зберігаються й читаються наступною сесією SQL.
2. Налаштування `email_reminders_enabled` і `message_style` мають
   правильні значення за замовчуванням, ізольовані між акаунтами,
   зберігаються у PostgreSQL; null/недозволені значення отримують 422.
3. Хибний поточний пароль повертає 400 `CURRENT_PASSWORD_INCORRECT`,
   не анулює JWT. Успішна зміна анулює всі попередні JWT, старий пароль
   не входить, новий входить, чужа сесія лишається чинною.
4. PNG/JPEG аватар нормалізується до приватного JPEG ≤512 px і 256 KiB,
   відповідь має `Cache-Control: no-store`, інший користувач бачить 404.
   Некоректний файл/формат/розмір не перезаписує фото. Заміна збільшує
   версію, новий test-app читає те саме фото з PostgreSQL, повторне
   видалення ідемпотентне.
5. Синтетичний HEIC кодується через реальний `pillow-heif`,
   завантажується через приватний HTTP API й читається назад як JPEG.
   Це **не замінює** перевірки справжнього iPhone 24/48 Мпікселів.

## Блокер основного FastAPI

До інтеграції в production не заявляти, що профіль доступний:
`backend/app/main.py` поки не включає `profile.router`. За командним
ТЗ §10 **цей спільний файл інтегрує Софія**, зокрема:

```python
from backend.app.routers import profile
app.include_router(profile.router, prefix=API_PREFIX)
```

У `feat/profile` вже прибрано перевірки `is_blocked` з `auth.py` і
`security.py`, стару frontend-обробку `ACCOUNT_BLOCKED` та оновлено тести
JWT. Залежності профілю (Pillow/HEIC) й пошти Софії (Gmail API) збережено
разом у `requirements.txt`. Видалення старих адмінських маршрутів і їхніх
тестів містить **окремий PR №220 Софії**; після його злиття потрібні
синхронізація й повторний CI. Підключення `profile.router` в `main.py`
виконується за командним погодженням, після цього перевірити OpenAPI.
Історичні дані `is_blocked` не виправляти напряму в production Neon.

## Реальне приймання після deployment

Відомий SHA backend/frontend, Alembic revision, час розгортання й пристрій
записати у командний звіт. Не створювати тестові акаунти на бойовій БД
без погодження.

- На iPhone Safari зняти 24/48-Мпіксельне HEIC; вибрати, переглянути,
  завантажити, замінити, видалити. Зокрема перевірити фото, що перевищують
  5 MiB: вони мають давати зрозумілу помилку, а не зламати старе фото.
- Із двома тестовими акаунтами перевірити незалежність профілів/фото,
  налаштування, помилковий пароль без виходу та правильну зміну пароля
  зі скасуванням попередніх сесій на двох пристроях.
- Софія перезапускає API, після чого повторюється GET фото/профілю.
  Це окрема **жива** перевірка, а не симуляція новим FastAPI test-app.
- Перевірити поведінку при timeout, недоступній БД та анонімному доступі.
  Не зберігати персональні фото/паролі/токени як докази.
