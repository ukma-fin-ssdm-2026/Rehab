## Виявлений дефект

Головна, календар, цілі й статистика показують HTTP 401 після успішного входу.
Форма запису повертає UNAUTHORIZED та показує JSON помилки замість тексту.
Профіль при цьому показує поточний акаунт. Приймальна перевірка цих сценаріїв
не пройдена; це не позначається як успішна перевірка iPhone.

Причину підтверджено кодом: п'ять екранів надсилали демонстраційний
`Bearer user-42`, тоді як авторизація використовує підписаний JWT.
Запити переведено на наявний `apiRequest` Анастасії, який додає токен
поточної сесії, обробляє 401 та повертає текст серверної помилки.
Зміни не додають нові календарні функції або інший спосіб зберігання сесії.

## Перевірки виправлення до розгортання

- `npm run test:api`: 4 passed. До зміни тест заборони demo-токенів падав
  на п'яти екранах; після зміни проходить. Також перевірені поточний JWT,
  заголовки запису, callback завершення сесії на 401 і збереження сесії на
  звичайній відмові в адмінській ролі (403).
- `npm run typecheck`: успішно.
- `npm run lint`: 0 помилок, 5 попереджень про наявні React effects
  у головній, цілях, статистиці й двох адмінських екранах. Ці effects не змінено.
- `npm run export:web`: успішно.
- Незалежний огляд змін: без важливих/критичних зауважень.

У desktop-браузері перевірена локальна production-збірка на
`http://127.0.0.1:8081` з публічним API Render. Використано синтетичний акаунт:
реєстрація/вхід → головна → календар → цілі → статистика завантажуються без 401;
створений тестовий запис з'являється в календарі, головна оновлює показники.
Reload зберігає сесію; вихід і повторний вхід успішні. Це не повторна перевірка
на iPhone і не доказ розгортання виправлення на Render.

## Повторна перевірка після розгортання виправлення

- [ ] Головна й статистика завантажують дані без 401.
- [ ] Календар завантажує записи поточного користувача.
- [ ] Цілі завантажуються без 401.
- [ ] Тестовий запис зберігається й доступний після повернення до календаря.
- [ ] Помилки форми відображаються зрозумілим текстом.
- [ ] Профіль, reload, вихід і повторний вхід залишаються працездатними.

Нову збірку frontend потрібно розгорнути перед повторенням цих пунктів.
Перевірка локальної збірки або API не замінює повторний тест на iPhone.
Android не перевірявся. Скриншоти з персональними даними в репозиторій не додані.
