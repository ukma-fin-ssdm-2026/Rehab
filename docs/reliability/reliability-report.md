# Лабораторна №9 — командний звіт про надійність Rehab

Стан коду станом на 09.11.2026. Початковий аналіз ризиків: [scavenger-hunt.md](scavenger-hunt.md). Описані сценарії є результатами аналізу та тестів, а не твердженнями про інциденти в production.

## 1. Сім ризиків і їхній стан

| Ризик | Категорія | Критичність | Стан |
|---|---|---|---|
| R1 — HTTP-запит без дедлайну | B, E | Висока | Виправлено: дедлайн клієнта 30 с |
| R2 — некоректний JSON перериває обробку 401 | A | Середня | Виправлено: контрольована помилка та обробка 401 |
| R3 — відсутня перевірка структури відповіді календаря | C | Середня | Виправлено: перевірка контракту в `calendar.ts`, контрольована `INVALID_RESPONSE` |
| R4 — SQL-запит/блокування без ліміту | B, E | Висока (умовна) | Виправлено: ліміти транзакцій PostgreSQL |
| R5 — синхронна БД блокує async-завантаження аватара | E | Висока | Виправлено: збереження у threadpool |
| R6 — необмежений прохід поштової черги | E | Середня | Виправлено: пакет і м'який бюджет часу |
| R7 — прихована причина `ImportError` | A, D | Низька | Виправлено: класифікація помилок імпорту та логування |

Обраний основний набір виправлень: R1, R2, R3, R5, R6. Додатково виправлено R4 та R7.

## 2. До / після та патерни

### R1 — запит без дедлайну

**До:** `await fetch(url, options)` без спільного ліміту часу.

**Після:** `AbortController` і `Promise.race([performRequest(...), cancelled])`; таймер на 30 секунд охоплює заголовки й тіло. Повертається `ApiError(0, "REQUEST_TIMEOUT", ...)`, таймер і listener очищуються у `finally`.

**Патерн:** fail fast, timeout, guard clause. Автоматичного повтору POST немає: сервер міг виконати запис навіть після клієнтського тайм-ауту.

### R2 — пошкоджений JSON замість обробки 401

**До:** `await response.json()` до перевірки `response.ok` і сповіщення про недійсну сесію.

**Після:** перевірка 401 за заголовками до парсингу; `JSON.parse(text)` з вузьким перехопленням `SyntaxError`. Пошкоджене успішне тіло дає `INVALID_RESPONSE`, пошкоджене тіло HTTP-помилки — `HTTP_ERROR` із правильним статусом.

**Патерн:** fail fast, вузький catch, безпечне повідомлення без вмісту пошкодженої відповіді.

### R3 — неперевірений контракт відповіді календаря

**Ланцюг:** тригер — сервер повертає 200 і валідний JSON неправильної структури, наприклад `{"items": null}`. Несправність — `return payload as T` у `frontend/src/api/client.ts` лише обіцяє тип і нічого не перевіряє під час виконання. Помилка — `setEntries(result.items)` (`frontend/src/app/(tabs)/calendar.tsx`) кладе `null` у стан, де очікується `CalendarEntry[]`. Відмова — наступний рендер падає на `entries.map(...)`; `.catch` екрана цього не ловить, бо помилка виникає вже в рендері, а не в запиті.

**До:**
~~~ts
export const listEntries = (from: string, to: string): Promise<EntryPage> =>
  apiRequest(`/calendar/entries?from=...&to=...&limit=100&offset=0`);
~~~

**Після** (`frontend/src/api/calendar.ts`):
~~~ts
export async function listEntries(from: string, to: string): Promise<EntryPage> {
  const page: unknown = await apiRequest(`/calendar/entries?...`);
  if (!isEntryPage(page)) throw invalidCalendarResponse();
  return page;
}
~~~

`isEntryPage` перевіряє, що `items` — масив, `total`/`limit`/`offset` — невід'ємні цілі числа, а кожен запис відповідає контракту `EntryOut` бекенду: цілі `record_id`/`user_id`, дата `YYYY-MM-DD`, `status` і `trigger_category` з дозволених значень, `drinks` — масив напоїв із додатним цілим `volume_ml`, `comment` — рядок або `null`, `created_at` — рядок. Так само перевіряється `getEntry` (екран запису). Відповіді `createEntry`/`updateEntry` свідомо не відкидаються: запис на сервері вже відбувся, і помилка на клієнті підштовхнула б користувача до дубля. Спільний `client.ts` не змінювався.

**Вибір:** швидка відмова. Неправильні дані показувати не можна (порожній календар виглядав би як «немає записів», хоча вони є), тому краще чесна помилка. Порушення контракту логується через `console.warn` без вмісту відповіді, а користувач бачить безпечне повідомлення «Сервер повернув некоректні дані календаря».

**Патерни:** перевірка входу (зовнішня відповідь — теж вхід), guard clause, fail fast, логування, безпечне повідомлення.

### R4 — завислі SQL-запити й блокування

**До:** `connect_timeout=5` обмежував лише встановлення з'єднання.

**Після:** у `backend/app/db/session.py` під час початку транзакції виконуються `SET LOCAL statement_timeout = '10s'` і `SET LOCAL lock_timeout = '2s'`. `get_db` після відповідних `OperationalError` виконує rollback та повертає 503 `DATABASE_TIMEOUT`. Autocommit advisory lock job лишається без змін.

**Патерн:** fail fast, тайм-аут БД, rollback; автоматично повторювати запис не можна.

### R5 — блокування event loop під час завантаження фото

**До:** синхронні `lock_user_for_update`, `db.get` та `db.commit` виконувалися в `async def put_avatar`.

**Після:** `await run_in_threadpool(_save_avatar, db, user.user_id, processed)` переносить синхронну транзакцію в окремий потік, повертає готовий `AvatarUploadOut` без lazy ORM-доступу.

**Патерн:** ізоляція блокувальної операції, fail fast при помилці БД; некоректний частковий результат не повертається.

### R6 — довга пошта в одному HTTP-запиті

**До:**
~~~python
while True:
    current = clock()
    if current.astimezone(BUSINESS_TIMEZONE).date() != today:
        break
~~~

**Після:**
~~~python
MAX_DELIVERIES_PER_RUN = 25
MAX_RUN_SECONDS = 20.0
while len(seen) < max_deliveries:
    if monotonic_clock() - started_at >= max_duration_seconds:
        break
~~~

Захоплені листи рахуються незалежно від результату (`sent`/`skipped`/`failed`/`unknown`). Решта `pending` залишається на наступний запуск. Вже розпочатий `sender.send` не переривається: 20 секунд — **м'який бюджет**, а не жорсткий HTTP-дедлайн. Адреси й токени не записуються до логів.

**Патерн:** fail safe, обмежена пакетна обробка, контроль часу, журналювання; результат `unknown` **не** повторюється автоматично, щоб не дублювати листи.

### R7 — надто широкий catch імпорту

**До:**
~~~python
except ImportError:
    raise api_error(
        503, "REMINDERS_NOT_READY", "Створення нагадувань ще не підключено"
    ) from None
~~~

**Після:** `ModuleNotFoundError.name` перевіряє, чи відсутній сам `backend.app.services.reminders`. Лише тоді відповідь — `REMINDERS_NOT_READY`. Зламані внутрішні залежності та інші `ImportError` журналюються з traceback і повертають окрему безпечну 503 `REMINDERS_DEPENDENCY_ERROR`; причина зберігається в ланцюгу винятків (`from error`), але не потрапляє в HTTP-текст.

**Патерн:** fail fast, вузька класифікація збоїв, зрозумілий код помилки, логування. Для внутрішньої несправності не повертаємо фальшивий успіх.

## 3. Режими відмов і відновлення

| Ризик | Режим відмови | Що видно зовні | Відновлення |
|---|---|---|---|
| R1 | Повільна/зависла мережа | `REQUEST_TIMEOUT`, замість безкінечного loading | Перевірити стан запису, лише тоді повторити вручну |
| R2 | Обірваний JSON, зокрема 401 | Контрольована помилка й скидання чинної сесії на 401 | Повторний вхід або новий запит після відновлення API |
| R3 | 200 з неправильною структурою календаря | Стан помилки екрана з кнопкою повтору замість падіння рендеру | Повтор користувачем після виправлення бекенду/контракту; дані на сервері не змінюються |
| R4 | Тривалий SQL / row lock | 503 `DATABASE_TIMEOUT` на шляху `get_db` | Rollback, звільнення блокування, перевірка стану перед повтором |
| R5 | Повільне збереження аватара | Запит очікує або завершується помилкою; інші корутини не блокуються ним напряму | Звільнення БД/потоку, повтор після перевірки профілю |
| R6 | Велика черга / повільний Gmail | Часткові лічильники; без зайвого довгого обходу черги | Наступний job обробляє `pending`; `unknown` розбирають окремо |
| R7 | Відсутній модуль чи внутрішня залежність | 503 з відповідним кодом, без деталей внутрішньої помилки | Виправити модуль/залежність за traceback у серверному журналі, повторити job |

## 5. Межі реалізації

Для R3 перевірку контракту додано лише для читання календаря (`listEntries`, `getEntry`); інші read-екрани (цілі, повідомлення, профіль) так само покладаються на `payload as T`, і перевірку варто поширити на них за тим самим зразком. Для R6 бюджет у 20 секунд перевіряється між листами й не припиняє вже розпочате надсилання. Відтворення production-розкладу та реальне надсилання Gmail не входили до перевірок.

## Бонуси

### Бонус 2 — перевірка здоров'я сервісу

Маршрут `GET /health/dependencies` перевіряє PostgreSQL (`SELECT 1`) і доступність Gmail API через офіційний Discovery API (`GET`, тайм-аут 3 с). Якщо обидві залежності доступні, повертається HTTP 200 зі статусом `healthy`; за відмови хоча б однієї — HTTP 503 зі статусом `unhealthy` і окремими станами `database` та `gmail_api`. Відповідь не містить секретів чи деталей винятків. Маршрути `/health` і `/ready` не змінено. Перевірка Gmail підтверджує доступність публічного API, але не чинність OAuth-токена чи успіх надсилання листа.

Докази: `backend/app/routers/health.py`, `tests/reliability/test_health_dependencies.py` (7 тестів, зокрема ін'єкції `OperationalError`, тайм-ауту Gmail API та HTTP-помилки). GitHub Actions PR №260 завершилися успішно: CI Pipeline, Code Quality, Dependency Audit і Lab07 Traceability.
