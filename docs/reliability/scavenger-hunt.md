## Етап 2. Несправність → помилка → відмова

**Як читати ланцюг:** fault — дефект або недостатній захист у коді; error — некоректний внутрішній стан після активації дефекту; failure — порушення очікуваної поведінки, видиме користувачу або іншій системі. Тригер описано окремо: повільна мережа сама по собі не є дефектом нашого коду.

Критичність тут оцінює потенційний вплив: **висока** — може надовго заблокувати основний сценарій або вплинути на кілька запитів; **середня** — порушує окрему функцію чи відновлення після збою; **низька** — переважно погіршує діагностику. Це попередня оцінка, а не виміряна частота інцидентів.

### R1. Очікування API без дедлайну

- **Тригер:** сервер або мережа довго не завершують відповідь.
- **Fault:** apiRequest не встановлює власний дедлайн запиту.
- **Error:** Promise запиту й залежний стан завантаження залишаються незавершеними довше прийнятного для інтерфейсу часу.
- **Failure:** користувач бачить тривале завантаження календаря чи іншого екрана без своєчасного повідомлення про збій.
- **Критичність: висока.** Спільний клієнт використовується основними функціями; проблема затримує їх доступність. Це не доводить втрату даних.

### R2. Некоректний JSON перериває обробку HTTP-статусу

- **Тригер:** відповідь, зокрема 401, позначена application/json, але тіло містить обірваний чи некоректний JSON.
- **Fault:** парсинг тіла виконується до обробки HTTP-помилки без окремого захисту від помилки декодування.
- **Error:** виконання залишає apiRequest через виняток парсингу; для 401 клієнтський стан сесії не скидається через sessionInvalid.
- **Failure:** користувач бачить технічну помилку замість узгодженого повідомлення; у сценарії 401 інтерфейс може залишатися в стані входу й повторювати невдалі захищені запити. Серверний контроль доступу цим не обходиться.
- **Критичність: середня.** Порушено обробку збою та відновлення сесії за конкретної некоректної відповіді.

### R3. Порушений контракт успішної відповіді

- **Тригер:** сервер повертає 200 із валідним JSON неправильної структури, наприклад {"items": null} замість масиву записів календаря.
- **Fault:** payload as T замінює перевірку структури припущенням про тип.
- **Error:** у стан entries екрана календаря може потрапити null замість CalendarEntry[].
- **Failure:** наступний рендер із entries.map завершується винятком; календар не відображається належним чином.
- **Критичність: середня.** Можлива відмова конкретного екрана при порушенні контракту API; нормальні відповіді не активують цей сценарій.

### R4. SQL-запит або блокування без перевіреного ліміту часу

- **Тригер:** довгий SQL-запит або інша транзакція утримує потрібний row lock; серверні statement_timeout/lock_timeout також не налаштовані.
- **Fault:** застосунок задає лише connect_timeout і покладається на неперевірені зовнішні обмеження виконання SQL.
- **Error:** запит залишається активним або в очікуванні блокування, утримуючи з’єднання та ресурси обробника; за повторення таких ситуацій вільних з’єднань стає недостатньо.
- **Failure:** користувач довго не отримує результату збереження, а інші запити можуть завершуватися помилкою очікування з’єднання або зовнішнім тайм-аутом.
- **Критичність: висока, умовна.** Можливий вплив на багато запитів; під час статичного аналізу серверні налаштування `statement_timeout` і `lock_timeout` залишалися невідомими. У виправленні R4 ліміти задано на рівні транзакцій застосунку.

### R5. Блокування event loop під час збереження аватара

- **Тригер:** SQL-операція у put_avatar сповільнюється або очікує блокування рядка користувача.
- **Fault:** синхронні lock_user_for_update, db.get і db.commit викликаються безпосередньо в async def.
- **Error:** потік event loop конкретного worker зайнятий синхронним очікуванням БД і не може своєчасно виконувати інші корутини.
- **Failure:** завантаження аватара та інші запити, які потребують того самого event loop, затримуються; клієнти можуть отримати тайм-аут.
- **Критичність: висока.** Вплив може вийти за межі одного upload. За кількох worker це не означає автоматичне блокування всього сервісу.

### R6. Поштова черга перевищує бюджет HTTP-запиту

- **Тригер:** велика черга або багато повільних надсилань, кожне з яких окремо вкладається у свій тайм-аут.
- **Fault:** один виклик deliver_pending_reminders не має малого ліміту пакета чи загального дедлайну; HTTP-обробник чекає завершення всього проходу.
- **Error:** job залишається активним з утримуваним advisory lock довше бюджету HTTP-викликача або проксі.
- **Failure:** викликач не отримує підсумковий результат вчасно; повторний запуск отримує 409 JOB_ALREADY_RUNNING, якщо попередній ще працює.
- **Критичність: середня.** Порушується своєчасність і спостережуваність фонової функції. Тайм-аут викликача сам по собі не доводить припинення job або втрату листів.

### R7. Прихована причина помилки імпорту

- **Тригер:** reminders існує, але його внутрішній імпорт залежності завершується ImportError.
- **Fault:** загальний except ImportError не розрізняє відсутність цільового модуля та поломку його залежності; немає логування, використано from None.
- **Error:** усередині шляху обробки різні причини збою зведено до одного REMINDERS_NOT_READY без збереження причини у прикладному журналі.
- **Failure:** оператор бачить 503 з оманливим поясненням і не отримує потрібної діагностики для швидкого відновлення нагадувань.
- **Критичність: низька для самого маскування.** Воно ускладнює діагностику; початкова непрацездатність job спричинена зламаною залежністю, а не цим catch-блоком.

## Етап 3. R1 і R2

Виправлення реалізовано у `frontend/src/api/client.ts`, сценарії збоїв перевірено в `frontend/tests/api-reliability.test.cjs`.

### R1 — дедлайн і скасування

**Вибір:** швидка відмова після 30 секунд очікування. Неправильний успіх для запису календаря гірший за явне повідомлення про відсутність відповіді.

Клієнт поєднує зовнішній signal із власним AbortController; дедлайн охоплює fetch і читання тіла. Promise.race завершує клієнтське очікування навіть якщо транспорт не відреагував на abort. При дедлайні повертається ApiError зі status=0 (HTTP-відповіді може не бути) і code=REQUEST_TIMEOUT. Таймер і зовнішній listener прибираються у finally. Уже скасований запит не надсилається. Пізня відповідь після скасування не змінює стан сесії.

Автоматичних повторів немає. Клієнтський timeout не гарантує rollback на сервері: результат серверного запису після тайм-ауту може бути невизначеним. Порядок механізмів: дедлайн і скасування → контрольована помилка; повтори й fallback-дані не застосовуються.

**Ін’єкції збоїв і тести** у frontend/tests/api-reliability.test.cjs:

- `deadline bounds stalled headers without retrying a write` — транспорт не відповідає; керований таймер спричиняє REQUEST_TIMEOUT, signal скасовано, POST не повторено.
- `deadline bounds stalled body without retrying a write` — заголовки отримано, тіло зависло; той самий дедлайн завершує очікування.
- `caller cancellation ends a pending request and cleans its deadline` — зовнішній abort завершує очікування та скасовує транспорт.
- `already cancelled request never reaches transport` — не виконується жодного мережевого виклику.
- `a response arriving after timeout cannot invalidate the session` — пізній 401 не має побічного ефекту після дедлайну.
- `network failure is preserved and clears the deadline` — первинна мережева помилка не губиться.
- `successful JSON and empty 204 clear deadlines and caller listeners` — нормальна поведінка та очищення ресурсів збережені.

### R2 — контрольована помилка JSON і обробка 401

**Вибір:** не повертати успішні дані при пошкодженому JSON. Відмовити явно; для HTTP-помилки зберегти її статус і безпечне повідомлення.

Обробка 401 виконується після отримання заголовків, до читання тіла, зі збереженням перевірки актуального токена. Тіло читається як текст; окремий вузький catch обробляє SyntaxError від JSON.parse. Для успішного HTTP-статусу пошкоджений JSON перетворюється на ApiError INVALID_RESPONSE; для помилки HTTP формується звичайна ApiError HTTP_ERROR зі справжнім статусом. Внутрішній текст SyntaxError та тіло пошкодженої відповіді не показуються користувачу. Структурну валідацію валідного JSON (R3) не додано.

**Тести** у frontend/tests/api-reliability.test.cjs:

- `malformed JSON at HTTP 200 produces a controlled error` — INVALID_RESPONSE замість успіху.
- `malformed JSON at HTTP 401 produces a controlled error` — статус збережено, актуальна сесія скидається.
- `malformed JSON at HTTP 500 produces a controlled error` — HTTP_ERROR замість витоку SyntaxError.
- `late malformed 401 cannot invalidate a newer session` — нова сесія залишається чинною.

### Фактична перевірка

До реалізації тести показали відсутність дедлайну та неконтрольовану SyntaxError при пошкодженому JSON. Після реалізації:

| Перевірка | Результат |
|---|---|
| npm run test:api | 103 тести пройшли, 0 помилок; з них 11 нових тестів надійності |
| npm run typecheck | успішно, exit 0 |
| npm run lint | успішно, exit 0 |
| git diff --check | успішно |

Існуючі VM-стенди тестів отримали AbortController і таймери. Перевірку тотожності об’єкта signal замінено перевіркою поведінки скасування, оскільки транспорт тепер отримує об’єднаний сигнал. Нових залежностей і змін lock-файлу немає. Живі сервери та мобільні пристрої не використовувалися; це локальна перевірка з керованим транспортом і таймерами.

## Етап 3. R6 і R7

### R6 — обмеження поштової черги

**До:** `deliver_pending_reminders` обробляла всі листи за один запуск у `while True`. Великі черги могли тримати HTTP-обробник та advisory lock довше часу відповіді.

**Після:** встановлено `MAX_DELIVERIES_PER_RUN = 25` і `MAX_RUN_SECONDS = 20.0`, а цикл зупиняється за кількістю захоплених листів або за монотонним часом. Між листами перевіряється дата за Києвом. Завершені надсилання записуються в БД; `pending` лишаються для наступного job, а `unknown` не надсилається повторно автоматично.

**Патерн:** безпечна часткова обробка (fail safe), бюджет часу, обмежений пакет та журналювання. 20 секунд — м'який бюджет: поточний Gmail-запит не переривається посеред надсилання.

**Тести:** вісім ізольованих сценаріїв у `tests/reliability/test_email_reminders_r6.py`, включно з повільним sender, невизначеним результатом, граничними лімітами й київською північчю. `tests/test_email_reminders.py` також перевіряє пакети 3+3+1 та звільнення advisory lock у PostgreSQL. GitHub Actions PR №257 завершилися успішно.

### R7 — діагностика помилки імпорту нагадувань

**До:** `except ImportError` приховував збої внутрішньої залежності як `REMINDERS_NOT_READY`, із `from None` і без журналювання справжньої причини.

**Після:** `ModuleNotFoundError.name` розрізняє відсутній цільовий модуль `backend.app.services.reminders` і відсутню внутрішню залежність. Для першого лишається `REMINDERS_NOT_READY`; для зламаних залежностей чи інших `ImportError` застосунок журналює traceback та повертає безпечну 503 `REMINDERS_DEPENDENCY_ERROR` без внутрішніх деталей.

**Патерн:** швидка відмова (fail fast), конкретна класифікація помилки та логування; немає фальшивого успіху чи беззмістовного fallback.

**Тести:** `tests/reliability/test_jobs_r7.py` — успішний імпорт, відсутній основний модуль, зламана внутрішня залежність, `ImportError` та HTTP-відповідь без витоку причини. GitHub Actions PR №257 завершилися успішно.

## Що не вважаємо дефектом без додаткових доказів

- `except BaseException` у get_db робить rollback і повторно піднімає виняток; це не мовчазне приховування.
- `except Exception` у calendar_postgres._write також робить rollback і raise.
- Поштова черга свідомо переводить невизначений результат у unknown без автоматичного повтору, щоб не дублювати листи.
- Ліміт розміру аватара та винесення нормалізації зображення у threadpool вже присутні.
