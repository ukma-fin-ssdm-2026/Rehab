## 1. Що це за проєкт і якою була мета

**Rehab** — демонстраційний мобільний застосунок для відстеження тверезих днів, фіксації вживання алкоголю, перегляду календаря, статистики та особистих цілей. Інтерфейс орієнтований на зрозумілу, підтримувальну взаємодію.

У межах погодженого обсягу потрібно було отримати **клікабельний прототип із 16 маршрутами**, а не повністю розгорнутий production-сервіс. Вимоги до робочого сценарію:

1. Відкрити демонстраційний екран входу та перейти на головну.
2. Створити запис за дату, указавши статус і, для дня вживання, кілька напоїв з об'ємом кожного.
3. Зберегти запис через справжній HTTP-запит до FastAPI.
4. Побачити цей запис у календарі.
5. Побачити зміни в статистиці, на головній і в прогресі цілі.
6. Відкрити всі 16 погоджених маршрутів, навіть якщо частина з них поки є заглушками.

Ключове правило — **взаємопов'язані показники мають походити зі спільних backend-даних**. Ми не хотіли чотири екрани з незалежними «намальованими» значеннями, які не змінюються після збереження запису.

### 2.1. Що змінилося у файловій структурі та чому

Раніше частина FastAPI-коду перебувала у старій структурі `src/api/`. Для прототипу **створено окремі кореневі каталоги `backend/` і `frontend/`**, щоб розділити сервер і застосунок. Робочий FastAPI перенесено та адаптовано під пакет **`backend/app/`**; тепер канонічна точка запуску — `backend.app.main:app`.

Frontend створено окремо в `frontend/`, а маршрути Expo Router розташовано в **`frontend/src/app/`**. Це дозволяє розробляти екрани, не змінюючи Python-код. Старі файли в `src/api/` могли залишатися в репозиторії для сумісності/історії; **запускати для прототипу слід саме `backend.app.main:app`**, не старий `src.api`.

Основні фактично задіяні шляхи:

```text
Rehab/
├── backend/
│   ├── app/
│   │   ├── main.py                 # FastAPI, підключення роутерів, CORS
│   │   ├── models.py               # Pydantic-схеми: записи, напої, статистика
│   │   ├── stubs.py                # демонстраційні дані у пам'яті
│   │   ├── routers/
│   │   │   ├── calendar.py          # календарні записи
│   │   │   ├── statistics.py        # GET статистики
│   │   │   └── ...                  # наявні маршрути, зокрема цілі
│   │   └── services/
│   │       ├── statistics.py        # розрахунок показників і прогресу цілей
│   │       └── ...
│   └── requirements.txt
├── frontend/
│   ├── src/
│   │   ├── app/
│   │   │   ├── login.tsx
│   │   │   ├── register.tsx
│   │   │   ├── onboarding.tsx

│   │   │   ├── (tabs)/              # шість вкладок
│   │   │   └── placeholders/        # шість профільних заглушок
```

**Чому обрали саме так:** це мінімізувало ризик змішування Python та TypeScript, дозволило створювати окремі PR і зберегти вже робочі маршрути календаря й цілей без непотрібного переписування. У старій технічній концепції трапляються інші, заплановані назви файлів і нових endpoint-ів. **Під час інтеграції орієнтувалися на фактично реалізований контракт**, а не на назви з чернетки.

## 3. Git: гілки, Pull Requests і правила інтеграції

Робота велася **без прямих змін у `main`**: для прототипу створено окрему інтеграційну гілку. Обидва учасники розробляли свої частини ізольовано, а перевірені зміни передавали через PR.

| Гілка | Призначення | Стан на дату звіту |
|---|---|---|
| `main` | Основна/стабільна історія репозиторію | Не використовувалася як base для PR прототипу |
| `feature/rehab-prototype` | Спільна версія Backend + Frontend | Обидва PR з КТ-5 об'єднано; перевірений локальний стан `9fda645` |
| `feature/backend-kt5-data` | Записи з напоями, статистика, автопрогрес цілей, CORS, тести | Опубліковано на GitHub; PR **#118** об'єднано |
| `feature/frontend-kt5-screens` | 16 екранів, форми, вкладки, підключення API | Frontend PR об'єднано в інтеграційну гілку |
| `feature/frontend-kt4-api-config` | Раніша конфігурація підключення Expo до API | Згадана під час `git fetch`; історична робоча гілка |

**Backend PR:** [#118 — «Додано записи з напоями та статистику тверезості»](https://github.com/ukma-fin-ssdm-2026/Rehab/pull/118).  
**Backend-коміт:** `f11141b` — `Додано записи з напоями та статистику тверезості`.  
**Ціль обох PR:** `base: feature/rehab-prototype`, **не** `main`.  
**Останній зафіксований локальний інтеграційний стан:** після `git fetch`, `git switch feature/rehab-prototype` і `git pull --ff-only` виконано fast-forward `f741e0e..9fda645`.

### 3.1. Як проходила інтеграція

1. Кожен учасник працював у своїй гілці, щоб не редагувати однакові файли одночасно.
2. Для Backend додано й перевірено новий функціонал, оформлено український коміт, виконано `git push -u origin feature/backend-kt5-data`.
3. Відкрито PR #118 до `feature/rehab-prototype`; GitHub показав **No conflicts with base branch**.
4. Після командного перегляду змерджено Backend PR #118, а потім Frontend PR.
5. На локальній машині оновлено інтеграційну гілку; Git підтвердив отримання **29 змінених/нових файлів** у виводі fast-forward, включно з Python і React Native.
6. Запущено автоматичні backend-тести, сервер і Expo Web, після чого команда перевірила переходи й наскрізну роботу даних.

**Чому такий порядок:** при проблемі після об'єднання можна швидше зрозуміти, чи пов'язана вона з API, чи з інтерфейсом. До спільної перевірки два окремі локальні дерева коду не гарантували, що застосунок працює як одне ціле.

## 4. Що реалізовано на Backend

### 4.1. Перенесення й збереження наявного API

- Робочий FastAPI організовано у `backend/app/` і налаштовано запуск через `python -m uvicorn backend.app.main:app`.
- Збережено наявні маршрути календаря та керування цілями; нову функціональність додавали до них, а не створювали паралельну несумісну систему записів.
- API використовує префікс `/api/v1`; Swagger доступний у `/docs`.
- Демонстраційні захищені запити використовують заголовок `Authorization: Bearer user-42`.

### 4.2. Записи з напоями та коментарями

Оновлено `backend/app/models.py` і `backend/app/routers/calendar.py`.

**Що додано:**

- `Drink` з полями `type` і `volume_ml`;
- можливість записати **кілька напоїв в одному календарному записі**;
- поле `comment` для текстової нотатки;
- збереження та повернення цих полів через API;
- перевірку додатного **цілого** значення `volume_ml`;
- очищення `drinks` при зміні статусу запису на `sober`;
- перевірку, що для `sober` не передають напої.

Приклад фактично узгодженого з Frontend запиту:

```http
POST /api/v1/calendar/entries
Authorization: Bearer user-42
Content-Type: application/json
```

```json
{
  "date": "2026-10-15",
  "status": "relapse",
  "trigger_category": "social",
  "drinks": [
    {"type": "beer", "volume_ml": 330},
    {"type": "wine", "volume_ml": 150}
  ],
  "comment": "Демонстраційний запис"
}
```

Доступні типи напоїв: `beer`, `wine`, `spirits`, `cocktail`, `other`. Статуси дня: `sober`, `relapse`. `trigger_category` — необов'язкове поле (`stress`, `holiday`, `social`, `other`) для дня `relapse`. `comment` — необов'язкове поле. Для `sober` список `drinks` має бути порожнім. Для сумісності зі старими запитами `drinks` може бути пропущено; у новій формі можна вимагати введення хоча б одного напою для `relapse`.

**Важливі правила:** один календарний запис на користувача й дату; повторне створення за тією самою датою дає `409 Conflict`; помилкові дані — `422`. Це зберігає зрозумілі правила для календаря і статистики. `user_id` не додається як довільне поле форми: сервер визначає демокористувача через тестовий Bearer-токен.

**Чому зроблено саме так:** спершу наявний запис містив тільки дату/статус/тригер, але форма прототипу мала підтримувати кілька напоїв та коментар. Розширення `EntryCreate` і `EntryOut` забезпечило відображення цих відомостей після повторного GET без втрати сумісності старого календарного API.

### 4.3. Статистика і цілі 7 → 30 днів

Створено:

- `backend/app/routers/statistics.py` — маршрут `GET /api/v1/statistics`;
- `backend/app/services/statistics.py` — розрахунки показників, серій і прогресу цілей;
- нові Pydantic-поля відповіді статистики в `backend/app/models.py`;
- облік стартової дати відстеження в `backend/app/stubs.py`;
- реєстрацію маршруту статистики в `backend/app/main.py`.

Маршрут приймає `period=all`, `period=week`, `period=month` або `period=year`. Схема відповіді містить:

| Поле | Значення |
|---|---|
| `period`, `period_start`, `period_end` | Обраний період і його межі |
| `tracking_start_date` | Дата початку демонстраційного відстеження |
| `sober_days`, `relapse_days` | Показники для обраного періоду |
| `total_sober_days` | Загальна кількість тверезих днів для прогресу |
| `current_streak`, `longest_streak` | Поточна й найдовша серії |
| `active_goal_days` | Активна ціль, зокрема 7 або 30 днів |
| `completed_goal_days` | Перелік завершених цілей |
| `goal_progress_days` | Прогрес активної цілі |

Розрахунок автоматичних демонстраційних цілей 7 → 30 днів виконують на основі серверної статистики. **Не потрібно створювати окреме незалежне значення прогресу в кожному екрані.** Історичні CRUD-маршрути `/api/v1/goals` залишені для сумісності; вони не є окремою реалізацією нової автоматичної послідовності.

**Навіщо окремий `services/statistics.py`:** винесення формул із HTTP-роутера дозволяє тестувати їх самостійно, підтримувати різні періоди та не дублювати бізнес-логіку в інтерфейсі.

### 4.4. CORS для Expo Web

У `backend/app/main.py` додано/уточнено CORS для адрес розробки:

- `http://localhost:8081`;
- `http://127.0.0.1:8081`.

Дозволені прикладні методи: **GET, POST, PATCH**; заголовки `Authorization`, `Content-Type` дозволені конфігурацією middleware. **OPTIONS** обробляється як браузерний CORS preflight автоматично — окремий прикладний endpoint для `OPTIONS` не потрібний.

**Чому це було важливо:** до злиття PR колега повідомила `OPTIONS /api/v1/calendar/entries → 400` та `Failed to fetch`, а `/api/v1/statistics → 404`. Це узгоджувалося із запуском старої гілки Backend: у PR #118 вже були відповідні CORS-налаштування й новий маршрут статистики. Після об'єднання та запуску актуального коду спільний сценарій підтверджено як робочий. У тестах попередньо перевірено preflight `200` і статистику `200`.

### 4.5. Демонстраційні дані

- Тимчасові записи зберігаються **в оперативній пам'яті Python-процесу**, а не в базі даних.
- `backend/app/stubs.py` містить демонстраційні початкові значення, зокрема стартову дату відстеження й тестові записи.
- Після перезапуску FastAPI дані можуть скинутися; це **очікуване обмеження прототипу**.

**Чому не додавали БД:** вимогою цього етапу була клікабельна демонстрація узгодженого сценарію. PostgreSQL, міграції й production-сховище створили б додаткову складність без потреби для КТ-5.

## 5. Що реалізовано на Frontend

Frontend створено на Expo/React Native/TypeScript із маршрутами у `frontend/src/app/`. Файли, отримані після merge, включають форми `login.tsx`, `register.tsx`, `onboarding.tsx`, `add-entry.tsx`; усі шість вкладок `(tabs)`; шість файлів `placeholders/`; спільний `ScreenPlaceholder.tsx` та `src/config/api.ts`.

- Є демонстраційні форми входу, реєстрації та початкового налаштування.
- Є головна сторінка і **шість вкладок нижньої навігації**.
- Форма `add-entry.tsx` надсилає узгоджені назви полів `date`, `status`, `trigger_category`, `drinks: [{type, volume_ml}]`, `comment`.
- Календар відображає записи, статистика — показники за період, а екран цілей — прогрес, пов'язаний із backend-даними.
- Профіль забезпечує навігацію до окремих демонстраційних сторінок.

**Чому спочатку перевіряли контракт:** це запобігло непомітній несумісності між React-формою та Pydantic (наприклад, `comment` проти `note`, або рядковий `volume_ml` замість цілого числа). Колега окремо підтвердила формат POST перед інтеграцією; змінювати Backend для цього не знадобилося.

| 16 | `placeholders/privacy.tsx` | **Заглушка** приватності та конфіденційності |

Технічний `index.tsx` використовується для початкової навігації/перенаправлення і **не рахується окремим 17-м продуктовим екраном**. Вкладка `friends-support.tsx` — десятий основний маршрут, але її внутрішня функціональність також поки демонстраційна. Таким чином, маємо **10 основних маршрутів + 6 окремих заглушок**, а не 16 повністю функціональних модулів.

## 7. Що ще НЕ реалізовано (свідомі обмеження)

Це не помилки або «забуті екрани»; це зафіксовані межі погодженого прототипу.

| Функціональність | Поточний стан |
|---|---|
| Production-вхід, реєстрація, JWT, відновлення пароля | **Не реалізовано.** Вхід/реєстрація — локальні демонстраційні переходи, `user-42` — тестовий Bearer-токен |
| Збереження реальних паролів і користувачів | **Не реалізовано**; справжні облікові дані не вводити як виробничі |
| Постійна база даних, резервні копії, синхронізація | **Не реалізовано**; серверні записи тимчасові (in-memory) |
| Реальне редагування профілю | **Заглушка:** `placeholders/edit-profile.tsx` |
| Реальна зміна пароля | **Заглушка:** `placeholders/change-password.tsx` |
| Реальні push-сповіщення та їх налаштування | **Заглушки:** `placeholders/notifications.tsx`, `placeholders/notification-vibe.tsx` |
| Центр допомоги, звернення до служби підтримки | **Заглушка:** `placeholders/help.tsx` |
| Налаштування приватності/конфіденційності акаунта | **Заглушка:** `placeholders/privacy.tsx` |
| Запити в друзі, списки друзів, особисті повідомлення, зв'язок із ментором | **Заглушка:** `(tabs)/friends-support.tsx`; повідомлення нікому не відправляються |
| Автоматичне сповіщення друга/ментора про рецидив | **Не реалізовано**; коментар лише зберігається в записі |
| Apple Watch, Mi Band та інші носимі пристрої | **Не реалізовано** |
| Production-сервіси, зовнішні платіжні системи | **Не реалізовано / не входять до обсягу** |
| Повний цикл security-аудиту та готовність до публічного розгортання | **Не підтверджено**; окремі попередження залежностей залишаються |

Принцип: заглушки мають чесно позначатися як майбутні функції, а не створювати видимість справжнього надсилання повідомлень, зміни пароля чи збереження профілю.

## 8. Перевірки, результати та відомі застереження

### 8.1. Backend: автоматичні тести

Після об'єднання обох PR у `feature/rehab-prototype` виконано з кореня проєкту:

```powershell
python -m pytest -q
```

**Фактичний результат:** `50 passed, 1 warning in 2.10s`.

- 14 попередніх тестів;
- 13 нових тестів у `tests/test_entry_details.py`;
- 23 нові тести у `tests/test_statistics.py`.

Нові тести перевіряють модель запису, кілька напоїв, валідацію, роботу календарного API та розрахунки статистики й цілей. Перед PR #118 були також успішні локальні перевірки `black --check`, Flake8 і `git diff --check` для відповідного Python-коду; це **не рівнозначно окремо перевіреному результату всіх GitHub Actions після merge**.

**Попередження:** `StarletteDeprecationWarning` щодо старої інтеграції `httpx` із `starlette.testclient`. Воно не спричинило падіння тестів, але може вимагати оновлення тестових залежностей у майбутньому.

### 8.2. API та CORS

Під час локальної перевірки оновленого Backend:

- Swagger `http://127.0.0.1:8000/docs` відкрився, маршрут `GET /api/v1/statistics` був присутній.
- `GET /api/v1/statistics?period=all` повернув `200` із JSON-показниками.
- CORS preflight для POST із дозволеним Expo Web origin перевірено з відповіддю `200`.

### 8.3. Інтеграція React Native / Expo

Після merge виконано:

```powershell
cd frontend
npm ci
npx expo start --web
```

- Залежності встановлено (`569 packages` у зафіксованому запуску).
- Expo Web запустився; Backend працював паралельно на порту `8000`.
- Команда повідомила, що **всі вкладки/переходи працюють**.
- Команда повідомила, що **збереження запису змінює календар, статистику та прогрес цілей**.
- Frontend-розробниця повідомила, що TypeScript-перевірка `npx tsc --noEmit` пройшла; її окремого логу в цьому звіті немає.

**Застереження залежностей:** `npm ci` показав `28 vulnerabilities (10 moderate, 18 high)` та попередження про застарілу залежність `uuid`. Це **не усунуто** й має бути предметом окремого аудиту; автоматичне `npm audit fix --force` не запускалося, щоб без оцінки не зламати сумісність Expo. Не слід називати прототип перевіреним для production.

### 8.4. Що ще варто перевірити на КТ-6

За внутрішнім планом КТ-6 присвячена фінальній демонстрації та стабілізації. Залишаються не зафіксовані як пройдені перевірки:

1. **Чистий запуск** на іншому комп'ютері тільки за інструкцією з [`SETUP_AND_RUN.md`](SETUP_AND_RUN.md).
2. Запуск і повний сценарій **на фізичному телефоні**, якщо це потрібно для демонстрації; поточне підтвердження стосується Expo **Web**.
3. Некоректні форми, сервер недоступний, `401`, `409`, `422`, повідомлення користувачу та повторне відкриття екранів.
4. Результати GitHub Actions та аналіз попереджень `npm audit`.
5. Достатність README, інструкцій запуску й запису фактичних результатів фінального демо.

Цей перелік **не додає нових продуктових функцій**. Він потрібний, щоб не плутати успішне ручне тестування основного сценарію з повною завершеністю перевірок.

Підготовлені макети є попередньою концепцією майбутнього інтерфейсу Rehab, а не остаточно затвердженою реалізацією.

Дизайн у Figma та функціональний прототип Expo мають різний обсяг: у Figma представлено 14 макетів, а в програмному прототипі створено 16 маршрутів, частина яких є демонстраційними заглушками.

Окремі можливості, зображені в макетах, зокрема взаємодія з ментором, сповіщення та відстеження активного епізоду, ще не реалізовані як повноцінні функції.

Матеріали Figma слугуватимуть орієнтиром для подальшого вдосконалення UI/UX та узгодження вигляду застосунку.
